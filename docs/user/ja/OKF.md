# OKF — Open Knowledge Format

最終更新: 2026-09-04

OKF（Open Knowledge Format）は、Markdownの知識コレクションのためのオープンな規約です: 小さく統一されたFrontmatterヘッダーを持つ、純粋なMarkdownファイルです。このページでは、OKFとは何か、Plainvaが自動的に何を行うのか——そして、なぜあなたがそれらを*使う必要がない*のかを説明します。

## OKFとは？

その考え方は: 保管庫内のすべてのドキュメントが、それ自身で何であるかを示すということです。そのためには、Frontmatterの最小限のヘッダーだけで十分です。

```markdown
---
type: Note
---
# My note
```

- **`type`**——このドキュメントがどのような種類か（例: `Note`、`Daily Note`、`Project`）。規約の唯一の必須フィールドです。
- **`okf_version`**——保管庫がどのバージョンの規約に従っているかを示します。この値は**一度だけ**、ルートの`index.md`に置かれ（現在は`"0.2"`）、個々のノートには置かれません。
- **`index.md`**——各フォルダーは、その目次として1つの`index.md`を持つことができます。`index.md`と`log.md`という名前はこのために予約されており、通常のノートには使用すべきではありません。

> ツールやスクリプトでファイルを書きますか？ 正確なフィールド契約——許可される値、各プロパティタイプがどのようにシリアライズされるか、予約名のルール——は[ファイル形式リファレンス](File_Format_Reference.md)にあります。

**OKFの由来:** OKFはGoogle Cloudによるオープンな仕様です（[`GoogleCloudPlatform/knowledge-catalog`](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)、Apache-2.0ライセンス）。Plainvaは**OKF 0.2**（2026年7月25日公開）に従います。0.2で新しく追加されたのは、ノートがどこから来たのか、誰かがレビューしたのか、まだ有効なのかを示す5つの任意フィールドです——`generated`、`verified`、`sources`、`stale_after`、`status`。Plainvaがそれらについて何を表示し何を書き込むかは、下の「出所、レビュー、ライフサイクル」で説明します。

## なぜPlainvaはOKFを使うのか？

純粋なMarkdownは驚くほどポータブルです——しかしそれだけでは信頼できる構造を持ちません。OKFはそこに必要最小限の構造を加えるだけで、すべては標準的なFrontmatterを持つ、ごく普通のMarkdownのままです:

- **データベース、フィルター、テンプレートは構造に依拠できます。** すべてのノートが`type`を持つため、普通のファイルに対する`.base`ビューも堅牢であり続けます。
- **フォルダーはナビゲート可能なままです。** フォルダーごとの`index.md`という目次は、人にもツールにも役立ちます。
- **スクリプトやAIアシスタントも保管庫を安全に扱えます**——ディスク上の形式が統一され、文書化されているためです。
- **ロックインなし。** OKFは、ごく普通のMarkdownの上に成り立つオープンな規約です——他のOKFツールも、今日そして10年後もあなたのファイルを理解できます。

## Plainvaが自動的に行うこと

**新規ファイル**にはOKFヘッダーが自動的に付与されます: Plainvaで作成されたすべてのノートは、そのFrontmatterに`type`を受け取ります——OKF 0.2以降、バージョン指標である`okf_version`はルートの`index.md`に一度だけ置かれ、個々のノートにはもう置かれません。値は保管庫ごとに設定できます: **設定 → 保管庫 → コンテンツと構造 → OKF（Open Knowledge Format）** → **新規ノートのtype**（デフォルトは`Note`）と**デイリーノートのtype**（デフォルトは`Daily Note`）。テンプレートが独自の`type`を持っている場合は、テンプレートが優先されます。

**既存のファイルは無断で変更されることはありません。** Plainvaは、新規ファイルを作成する際、またはあなたが明示的に変換を開始した場合にのみ、OKFフィールドを追加します。

**保護されたシステムフィールド:** **プロパティ**パネルでは、`type`と——古いノートにまだ残っている場合は——`okf_version`がOKFシステムフィールド（「OKFシステムフィールド——Plainvaによって管理されています」）としてマークされています: `type`の値は既知のタイプのドロップダウンから選択でき、`okf_version`は表示のみです。規約が誤って壊れないよう、名前変更、タイプの変更、削除はロックされています。

**説明モーダル:** 設定内の**OKFとは？**が、3つの文での短い要約とこのページへのリンクを示します。もう自動的には開きません。保管庫にOKF形式に適合していないファイルが含まれている場合、Plainvaは一度だけ小さなメッセージでそのことを知らせ、変換へ直接移動できるボタンを表示します。

## 出所、レビュー、ライフサイクル（OKF 0.2）

OKF 0.2以降、ノートは自分がどこから来たのか、誰がレビューしたのか、まだ有効なのかを示せます。Plainvaはこれを3つのことに変えます:

**Plainvaが表示すること。**

- `status: draft`または`status: deprecated`を持つノートは、ドキュメントヘッダーに**下書き**または**廃止**の帯表示を持ちます。`stable`は表示されません。他の値を持つ独自の`status`列（例えばタスクデータベースの`Open`）はライフサイクルの状態ではなく、帯表示は付きません。
- `stale_after`を過ぎると、ノートの上に**失効としてマークされています（… 以降）**という通知が、プロパティへのジャンプ（**プロパティを開く**）とともに表示されます。この通知は表示のみです——Plainvaはノートの内容を何も変更しません。
- プロパティパネルの**信頼性と出所**セクション（スマートフォンでは、ノートのコンテキストシートの中）は、各フィールドをまとめ、それらから信頼度を導き出します: **未検証**、**機械により確認済み**、**人によるレビュー済み**——加えて生成（**生成**）、検証（**検証**）のリスト、クリックできるリンクとしての出典（**出典**）、ステータス（**ステータス**）、失効日（**失効日**）。 **ステータス**、**失効日**、**OKFバージョン** の各行は翻訳されたラベルで表示されます。ファイルに書かれるキー（`status`、`stale_after`、`okf_version`）は鍵アイコンのヒントに表示され、変わることはありません。

**Plainvaが書き込むこと。**

- `generated`（そして出典が分かる場合は`sources`）は、正確に3つの機械による書き込み経路によって設定されます: **インポーター**（`plainva-import/<version>`、実行ごとに1つの時刻——インポートレポートにも記録されます）、**メール取り込み**（`plainva-mail-capture/<version>`、メッセージのMessage-IDを出典として）、**タスク同期**（`plainva-task-sync/<version>`、ノートを新規作成するときのみ）。
- `verified`は**信頼性と出所**セクションの**確認済みにする**によってのみ書き込まれます: Plainvaは現在の時刻とともに`human:<あなたの名前>`をリストに追加します——2回目のレビューが1回目を上書きすることはありません。名前は保管庫ごとに一度尋ねられ、この端末に保存されます。**設定 → 保管庫 → コンテンツと構造 → 確認者名**で変更できます。
- エディターはこれらのフィールドを自ら触れることはなく、既存のノートが後から書き換えられることもありません。`status`と`stale_after`はプロパティとして、またはフロントマターで自分で設定するものです。

**バンドルのバージョンを更新する。** 規約のバージョンはルートの`index.md`に一度だけ置かれます。まだ`"0.1"`を宣言している保管庫はそのまま変わらず動作します——**設定 → 保管庫 → コンテンツと構造 → バンドルのバージョン**（スマートフォンでは: **設定 → Vault → メンテナンス → バンドルのバージョン**）で、**更新…**を使って0.2に引き上げます。ダイアログは事前に何が変わるかを示します: ルートの`index.md`内の行、そしてチェックボックス（デフォルトでオン）として、まだ残っている旧`okf_version`フィールドをノートから削除すること。すべてのファイルは変更前にバックアップされます。**クリーンアップ…**は2つ目の部分だけを行います。フィールド表と書き込みルールの詳細は[ファイル形式リファレンス](File_Format_Reference.md)にあります。

## index.md: フォルダーごとの目次

`index.md`はフォルダーの目次です: そのフォルダーに含まれるノートとサブフォルダーの一覧で、説明と相対リンクが付いています。

- **生成**——常にあなたの操作に応じて、何もないところから自動的に生成されることはありません: フォルダーを右クリック → **index.mdを生成/更新**、またはまとめて**index.md管理**（**設定 → 保管庫 → コンテンツと構造**）から行います。
- **生成の代わりに採用する**——既に概要ノート（MOC、概要、フォルダーノート、READMEなど）がある場合、管理画面がそれらを候補として提案します。**採用**は、そのファイルを`index.md`に名前変更し（リンクは保管庫全体で更新されます）、任意でOKF向けに整えることもできます。
- **自動的な保守**——Plainvaによって*生成された*一覧には、ファイルの末尾に不可視のマーカー（HTMLコメント）が付きます。このようにマークされたファイルのみ、フォルダーが変更されるたびに自動的に最新の状態に保たれます——そしてそれはOKF保管庫でのみです（ルートの`index.md`に`okf_version`があることで識別されます）。
- **読み取り専用と抜け道**——管理されているindex.mdファイルは、「このindex.mdはPlainvaによって管理され、自動的に更新されます」というバナー付きの閲覧モードで開きます。そこでは**更新**を行うか——**それでも編集する**を選択できます: これによりマーカーが削除され、そのファイルは再び完全にあなたのものになります（自動更新はされなくなります）。
- **一括処理**——**すべてのindex.mdを更新**は、保管庫のルートのコンテキストメニューと設定にあります。マーカーのないファイルはスキップされます。
- **抜けを埋める**——index.md管理の中で、**index.mdがないすべてのフォルダーに作成**を使うと、まだindex.mdがないフォルダーがすべてあらかじめ選択されるので、一度の操作でまとめて作成できます。
- **スマートフォンでは** — 同じことを二つの入口から。フォルダーを長押しすると、そのフォルダーに必要なほうに応じて**概要を作成**または**概要を更新**が示されます。保管庫全体をまとめて整えるときは **設定 → 保管庫 → メンテナンス → 概要** へ。概要のないフォルダーが先頭に並び、**index.md がない N 個すべてのフォルダーに作成**が一度に作ります。`index.md` を自分で書いたフォルダーは一覧に出ますが手は付けられません——引き継ぎはその一覧における名前の付いた判断であり、タップの副作用ではありません。自動更新もスマートフォンで動くようになりました。そこで編集した保管庫が、デスクトップで開くまで古いままということはもうありません。
- 閲覧モードでは、管理されている一覧はファイル/フォルダーアイコン付きのカードとしてレンダリングされます。リンクはPlainva内で直接開きます。

## 既存の保管庫を変換する（オプトイン）

保管庫内のファイルがOKF形式に適合していない場合（`type`フィールドの欠落、または予約名が通常のノートとして使われている場合）、Plainvaは変換を提案します——保管庫を開いたときに一度、そして**設定 → 保管庫 → コンテンツと構造**で恒久的に（この項目は、何かすべきことがある間のみ表示されます）。

**OKF形式に変換**ウィザードは、明確なステップで動作します。

1. **スキャン**——影響を受けるファイル数を表示します（テンプレートフォルダーとシステムフォルダーは除外されます。Frontmatterが読み取れないファイルはスキップされ、決して「修復」されません）。
2. **決定**——typeがないファイルのデフォルト`type`。既存の`type`の値は**そのまま使用**（推奨——既に有効なOKFタイプです）するか、別のフィールドに名前変更できます。
3. **プレビュー（変更なし）**——ドライランで、何が変更されるかを事前に確認できます。
4. **変換**——各ファイルは変更前に`.plainva/backups/`にバックアップされます。レポートには、何が変更され、何がスキップされたか、そしてバックアップフォルダーが要約されます。その後、任意で**index.md管理へ進む**ことができます。

ウィザードからのヒント: 変更は通常通り同期されます——Git保管庫の場合は事前にコミットしてください。

### スマートフォンで

同じ経路はモバイルにもあります。**設定 → Vault → メンテナンス → OKF形式に変換**。手順は同じです——スキャン、選択、プレビュー、変換——そして何かが書き込まれる前に、プレビューが対象のノートを名前で示します。

スマートフォンはいつでもアプリをメモリから外せるため、二つの仕組みが加わります。

- **一時停止と続行。** **一時停止**をタップするか、アプリがバックグラウンドに回ると、処理は次のファイルで止まります。続行しても書き込み先は同じバックアップフォルダーです——二つ目はできません。
- **起動時に尋ねる。** 処理が未完了のままなら、次にVaultを開いたときにPlainvaがそのことを伝え、**続行**または**元に戻す**を提示します。**あとで**も正当な答えです。中断された処理が残すのは、途中まで変換されたVaultであって、壊れたVaultではありません。追加されるのはfrontmatterのフィールドだけで、どのノートも有効なMarkdownのままです。

**元に戻す**はバックアップフォルダーからファイルを復元します——デスクトップでも同様に、処理後のレポートから行えます。バックアップフォルダーはその後も残ります。変換前の状態の唯一のコピーだからです。

## OKFを使う必要があるか？

いいえ。OKFは緩やかな標準です。

- 新規ファイルには自動的にヘッダーが付与されます——これが邪魔になることはなく、コストもかかりません。
- 既存の保管庫（例えばObsidianからのもの）は変更なく引き続き機能します。変換は厳密にオプトインです。
- `okf_version`が欠落している——あるいは古いノートにまだ残っている——だけでは違反とは見なされません。PlainvaとObsidianを永続的に並行して使用でき、繰り返し通知されることもありません。
- Obsidianや他のあらゆるエディターは、引き続きすべてのファイルを開くことができます: それは今も昔もごく普通のMarkdownです。
