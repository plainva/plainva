# Failed AI requests and what the assistant reads of a mail

Status: 2026-11-27 (plan Umsetzung 0.9.x, B7). Two rules, each written down as a table before the code that holds it:

1. **"Nothing was sent" is a fact of the run.** The assistant withdraws a typed question and says that nothing was sent only where nothing of the run left the device (table 1).
2. **The assistant reads of a mail only what the reader shows a person** — judged by the engine of the device, at the widths that are measured, with the limits that remain (table 2).

## 1. What can leave the device in one run

A *run* is one message the user sent (or "Send again"): the context is put together, the send overview may ask, the model is called, tools may run, the run is written. **The rule:** what the app says about sending holds for the words of this request — from typing to the end of its run — and for every way out of the device, not only the models' egress.

The table starts from the transports: every way the AI side of the app has out of the device. The AI session reaches the shell only through its hosts (`AiSessionHost`, `AiMcpHost`, `AiVaultHost` in `aiSession.ts` and `mcpSession.ts`); every member of them is either one of these transports or stays on the device, and `apps/desktop/src/ai/aiEgressOneWay.test.ts` fails where a member is added that this table does not name.

| Transport | Host member | Where it is used | Can it carry the user's words before a typed run asks its model? | In the run's list (`departedTo`) as |
|---|---|---|---|---|
| Model egress (chat, search model, reader without tools, a page's processing, transcription) | `AiSessionHost.egress` → the session's `this.out` | a run hands its own egress (`runDepartures`) to every request it makes: `runAgent`, `createPrivateDataExecutor`, `createWebExecutor`, and the question's way to a search model (`contextOf` → `candidates` → `gatherCandidates` → `semanticCandidates` → `rankedSearch` → `embed` → `send`) | **yes**: the question embedded for a cloud search model | the endpoint id (`openai`, `custom-1`) |

| External agents (ACP) | `AiSessionHost.acp`, `AiVaultHost.agents` | a conversation of their own with another maker's program | not part of a typed run: never withdrawn, never "nothing was sent" | — |
| Scripts | `AiSessionHost.scripts` | a closed box on the device; what a script calls are the conversation's tools above | no | (their tools' rows) |
| The calendar | `AiVaultHost.tools` (`get_calendar`, `get_event`) | read from the device's store (`pim.cache`) | no: nothing leaves | — |
| Everything else of the hosts (settings, stores, the index, the vault's files, replies written into a note) | the remaining members | on the device | no | — |

**The fact.** Each run gets its own list (`runDepartures` in `aiSession.ts`): a run of a server's prompt starts with that server in it; the run's egress — the session's, wrapped by `departingEgress` — adds every model request to a recipient that is not on this device, unless the egress answered it "never sent" (a refusal of the first class, `failureClassOf`) before anything came back; a request that throws, is cancelled, or ends in any other way counts; a foreign server's tool call, a read of a server skill's file, a page fetch and a mail search add themselves where the run takes them (`run.note`). The run hands its egress explicitly to every request it makes — nothing reaches it through a state of the session ("the run under way"); two runs of a message never run at once in a session (`send`, `replyInThread`, `runRoutine` say "busy"), and should they, each would count only its own. The turn of a typed question is withdrawn only where the list stayed empty; what the device sends for anything else at the same time counts for no run. The question's embedding goes out in a request of its own, never in a batch with the notes' embedding, and is never taken from a store of earlier questions (`rankedSearch` embeds each question anew).

**The list belongs to the turn, not to the try (review B7-3, S6).** Each run keeps whom it reached with the conversation (`RunMeta.departedTo`, read back by `readConversationRecord`), and "Send again" of the same turn starts with that list — also after a restart, and also where the device refuses the new try before anything is built (the early refusals in `runMessage`, "Fully local" among them, carry it on their notice). A refusal of the new try says nothing about sending then.

**"Send again" goes where the screen points (review B7-4, M-R4-1).** What the screen shows as the target is the target: "Send again" sends the turn to the model the conversation shows now (`retryLast` takes `choice()`), not to the model of the try that failed. **A try belongs wholly to its recipient (review B7-5, S-R5-1):** of the failed try it inherits only the content (the turn's parts, the sources that went, the size); everything it measures, asks, shows and keeps is the recipient's of this try — `runMessage` stamps the failed try's manifest for it (`restampedFor`: provider, label, model, `local`, price, the tools and the internet this model is given, the memory's lookup), so `scopeGrowth` measures the new recipient against what was confirmed, the send overview names it (and marks pictures it reads none of, `blind`), the run keeps it, and `keptOnDevice` reads the run as the one it was. The content may stay: the gate tells a cloud from this device only (`gateDecision`), a conversation that ran here never goes to a cloud, and an unknown model sends nothing. Where putting the context together does tell one model from another, the retry keeps what was put together and lets the new model's own check decide: the package's budget follows the model's window (`contextBudgetFor(windowOf(…))`, `carriedTokens`) — a try at a model with a smaller stated window is refused before it goes (`window_too_small`, through `told.window`), the system's own model cuts the request to its window (`told.contextTokens`), and nothing is put together anew; whether a model takes tools (`toolless`) and pictures (`blind` in the overview) is the new model's. No rule of the gate names a provider or a model. The send overview asks first where more would go than was confirmed for the new recipient, and always where the device asks before every request. The table test `aiRetryRecipient.test.ts` holds it for {a cloud model, a model on this device} × {another model of the same provider, a cloud never approved, a cloud approved before, a model on this device, an unknown one} × "Ask before every request" × "Fully local": whom it was sent to, whether and for whom the overview asked, whom the run's record names and whom the notice names agree in every cell. A notice names the provider of the try it speaks of (`notice.choice`), whatever model the conversation shows by then. A conversation that ran on this device stays there (`kept_on_device`), "Send again" included.

**Before the model call**, the list can hold: for a typed run, at most the provider of the search model (requests to it are one entry however often they are repeated); for a run of a server's prompt, that server, and the search model's provider where its text went to the search; for "Send again", whatever the turn's earlier tries reached; for a routine, the provider of the search model (its request is searched while its context is put together) — never where the device asks before every request (below). None of these but a typed run with an empty list is ever withdrawn.

**Routines (review B7-3, S5).** A routine's run puts its context together — the search included — before it checks whether it would bring along more than its user confirmed. Where it stops there, its run record notes that something had left (`RoutineRun.departed`), and its line in the list says "would send more than you confirmed" without "Nothing was sent." (`routineRows`). The routine's confirmation (`routinePreview`) puts the same context together and therefore asks the search model too: the scope the user confirms rests on what the search finds. That cannot be left out without confirming a scope the runs would then outgrow; what the confirmation says about it is a text still to be decided (the template of wordings).

**While the device asks before every request (review B7-4, M-R4-5)** a routine with a model off this device does not run: nobody is there to answer. It now rests before anything is put together — `routineRun` asks what `routineNeed` asks (`confirmEveryRequest` and a model not on this device) before `runMessage`, so its request reaches no search model either, and its line says "did not run: it needed you" truly. Its confirmation then puts its context together with the egress that sends nothing off this device (`runMessage(…, { held: true })` → `deviceOnlyEgress`): the search model is not asked, and the confirmation says the routine rests (`everyRequest`).

**The guard.** `apps/desktop/src/ai/aiEgressOneWay.test.ts` reads the sources: the desktop's `ai_http` is called in its egress alone, the phone's `AiNet` plugin is reached in its egress alone, each shell makes its egress once and hands it to `new AiSession`, the session takes it in one place, behind the device's switch. Inside `runMessage` and `execute` no other egress than the run's is named — nor in any method they reach, step by step through the calls on `this` (review B7-4, M-R4-4: `contextOf`, `memoryStart`, `styleStart`, `furtherTools`, `serverSkills`, `skillRuntime` and the rest; only `runDepartures` and `deviceOnlyEgress`, which make a run's egress, name the session's); those methods reach the hosts only through the members table 1 names, never by a cast, a destructuring, an alias of `this` or a computed member; every `execute` is handed a run's list; the question's way to a search model hands the run's egress on at each step; every member of the session's hosts is named in this table. The types hold the search's way too: `candidates`, `gatherCandidates` and `semanticCandidates` cannot be called without an egress. It follows every `this.name` a body names, called or handed on as a value (`.call(this, …)`, `forEach(this.name, this)`), and class fields that hold an arrow function; it refuses `this` handed to a function as an argument and `.call`/`.apply`/`.bind` with `this` (review B7-5, H-R5-1). **Limit:** the guard reads source patterns; a host reached through another object, a method reached through a variable that holds it, or code outside the session's file that is handed the session some other way, is not followed. It is a tripwire for the ways a change is likely to take, not a proof; the tests of the runs (`aiSendingFacts.test.ts` and the others) hold the behaviour.

**What the guard leaves to the tests (N1).** A run counts as typed only without a server's prompt (`!server` among the conditions of `typed`). Without that condition a server's prompt run would be treated as typed only where it is refused before anything is built (an unknown endpoint, "Fully local"): the server's text would then go back into the field as if the user had typed it. No sentence about sending changes with it — the run starts with the server in its list, so its notice claims nothing either way —, which is why the mutation lives in the tests' blind spot; the condition stays for what goes back into the field.

**When the model call never went but something left before it.** The turn stays (second class: "Send again" in place), the notice names no "nothing was sent": the four refusals whose words say so (`too_large`, `invalid_request`, `window_too_small`, `local_only`) keep their reason and their remedy, and their sentence about sending (`{{sent}}`) stays empty until a text of its own is decided (`aiFailureText`, `conversationFailureText`); `unreachable` says "Could not reach …" (`ai.error.offline`), `no_key` and `unknown_endpoint` say what they say (none of them claims nothing was sent). Whom the list holds is kept with the notice (`departedTo`) — before the model call the entries named in the paragraph above.

## 2. What the person sees in the mail reader, and what the engine measures

**The rule:** the measurement takes the reader as its measure, not the mail's source. For whatever the reader takes only from the loaded picture, the largest the reader allows holds.

The walk over the reader's tree (`htmlVisibleText.ts`) leaves out what an element hides by its own style. What only the place of other boxes hides is asked of the engine (`engineVisibility.ts`). The engine's frame is built by the reader's own builder (`buildMailFrameDoc`), with the reader's rules for pictures from one source (`MAIL_IMAGE_RULES` in `mailSanitize.ts`); a test holds that both frames take them from there.

| What decides what the person sees | Desktop | Phone / tablet | What the engine measures | Where it differs, what follows |
|---|---|---|---|---|
| Width of the reader | the frame is `width:100%` of the mail column (`mail.css`), any width; fitted (`applyFrameFit`) | the screen's width (portrait, landscape, split view, tablet), fitted with `growHeight` | 343 and 760 px, and the widths the readers of this device show mails in (`mailReaderWidths`): every reader frame on screen in this window (two mail panes side by side), then the latest widths kept on the device by any window within 30 days, at most three (`READER_WIDTHS_MEASURED`); noted at every fit by `MailView.tsx` and `MailMessageScreen.tsx` — before any mail was shown, the window's width | **Limit:** a width the person chooses later (a wider column, rotating the phone) can show differently from what the assistant read; before the first mail the window's width stands in for the column, which may be narrower. Named in the guide. |
| Height | the frame has its own height and scrolls | the frame grows (`growHeight`) | the frame grows (`growHeight`) | scrolling inside the desktop frame reaches every line the grown frame shows: a word below the fold is reached by scrolling; nothing is clipped by the frame's height (the frame scrolls, `overflow` stays the document's). |
| Pictures from the network | shown after the person's choice (per message or always) | the same | never loaded; where the reader leaves a size to the picture, it is measured **as large as the reader allows** (see below) | see "remote pictures" |
| Dark mode / the theme's canvas | the theme's colours only for a mail that sets none | the same | the white sheet | colours decide contrast, which the walk judges; the engine judges covering, which colours do not change |
| Font size, zoom | the app's zoom scales the window; the mail's own sizes stand | the system's text size does not reach the frame | the frame's own sizes | the app's zoom scales everything alike, nothing comes to lie over anything else |
| Text direction overrides (U+202D, U+202E, `<bdo>`, `unicode-bidi: bidi-override`) | drawn mirrored | the same | the text under the override is found | it is not read (see below); right-to-left text, embeddings (U+202A, U+202B) and isolates (U+2066–2069) are no override and are read |
| The engine the measurement runs in (WebKit on iPhone, iPad and the Mac; Chromium/WebView2 elsewhere) | — | — | the frame is laid out by the device's own engine; the pass asks each picture's own state (`complete`), never its `load` event, and lies in the window, invisible | see "the engine's own ways" below |
| Words shown in another order by invisible direction marks, without an override (U+200F, U+061C, embeddings, isolates, `dir="rtl"`) | drawn in another order | the same | — | read in the order of the text, as on `main` (the maintainer's decision (a), 27.11.; see below); the user guide names it |

**Remote pictures.** The engine loads nothing from the network. Which of a picture's sizes the reader fixes is not read from its markup — an attribute, a word in its style — but asked of the layout under the reader's rules: in the engine's frame each picture from the network is shown, in turn, with stand-ins of 1 × 1, 1 × 4000 and 4000 × 1 pixels (`remotePictureFreedom`). A width or height that changes between them is the picture's to set, as `height:auto`, `min-height`, a `height` attribute under the reader's `height:auto`, or no size at all leave it; such a size is then made as large as the reader allows: the width 100 % of its box, the height that of the whole mail laid out — `max-width` and `max-height` still bound them, as they would bound the loaded picture. A size that stays the same is the mail's and stays (a picture of `width:300px;height:4px` keeps it, in the reader too). That is as large as a picture can be where it can cover anything: a picture in the flow covers only words that run into it from before it — whatever follows it is pushed below it —, and nothing that runs out of an earlier box reaches further down than the mail itself. The gate loads a tall picture in the reader for every such form and holds that the assistant reads only words the pixel judge sees with the pictures and without them. **What it costs:** where the real picture is smaller than the largest the reader allows, a word it leaves visible can be left out — the safe way. The gate names three such forms as known costs (a logo without width beside a line that runs out of its box, a float with a negative margin, two pictures side by side) and reports how many words they lose; in ordinary newsletter forms (a logo, a picture held by `height:auto`, a picture beside text, icons in a line) it loses none.

**Cost.** Each text is first asked as a whole; only a text that meets something that paints, a later text, a clipping edge or the frame's edge is asked word by word. Every step of the pass — the boxes that paint, the texts, the words — asks for the interface's turn once 12 ms have passed, through a message task, which an engine does not throttle in a hidden or minimised window as it throttles timers (**limits**, `Performance_Notes.md`: a mail of thousands of painting boxes still holds the interface for one task of about 150 ms while its texts are gathered, cause not found; in Chromium a single paragraph of 50,000 words runs past the budget — the assistant reads nothing of it — and 20,000 words that run into the next box hold one task of about 640 ms before the budget stops them, the first layout of one huge line; the gate measures the widest gap between two tasks with a message meter, in both engines, since WebKit gives no long-task entries); the pass has a budget of 3 seconds for a mail; past the budget the assistant reads nothing of the mail and is told that it was too long to check in time (`TOO_LONG_TO_CHECK_BODY`, not the notice for a message that cannot be shown safely). The budget is chosen from the measurement in `Performance_Notes.md` ("The mail engine pass for the assistant"); not measured on a real phone.

**Direction overrides.** A direction override (U+202D, U+202E up to U+202C, `<bdo>`, `unicode-bidi: bidi-override`) draws the letters in the order they are written whatever their direction: a person sees them mirrored, a machine reads them plainly — a known way to show text that only a machine reads. Its text is blanked for the assistant. Right-to-left mail does not use it: Arabic and Hebrew run through the bidirectional algorithm, `dir="rtl"`, embeddings and isolates, none of which is an override; the gate holds that such mails keep every word.

**Words shown in another order without an override (decided 27.11.: (a), as on `main`).** Invisible direction marks, embeddings and isolates (U+200F, U+061C, U+202B … U+202C, U+2067 … U+2069), or a `dir="rtl"` box, can show words on screen in another order than they stand in the text: a person who reads only left to right may read "SECOND FIRST" where the text says "FIRST SECOND". The assistant reads every word the reader shows, in the order of the text; it does not try to find such words. Rounds 2 to 5 of the review tried, and every form had two faults at once (review B7-5, S-R5-2 and S-R5-3): a single invisible character got round it, and ordinary Hebrew and Arabic mails lost visible Latin words that `main` reads (a list of brands that wraps on a phone, a signature line "Name, title", a cell). Who reads a line from the right reads it in the order of the text; the app cannot know who reads. So the finding is gone, not switched off (`WordOrder`, `letterSeen`, `backdropOf`, the line and block logic), and the user guide states the limit in one sentence. What stays of the measurement: hidden and covered words, and words a direction override draws mirrored (above). The gate holds both: `direction override` keeps the overrides hidden and one case of each kind the earlier rounds left out (an isolate, a right-to-left span with `bdi` in a left-to-right paragraph, a right-to-left box of Latin words with invisible marks) read in the order of the text; `right-to-left mail as it is written` holds 38 ordinary right-to-left mails — this branch's 24 and the reviewer's 14 of round 5 (Hebrew, Arabic, Persian, Urdu; buttons, columns, cells, signatures, lists that wrap, gradients) — at 343 and 760 px in both engines: every word the reader shows is read.

**Cost.** Measured 27.11. after the finding of words shown in another order was removed (the reviewer's cost probe of round 5, in Playwright's Chromium and WebKit 2388, all widths together; `Performance_Notes.md`): right-to-left mail now costs what left-to-right mail costs — 50,000 words in 1,000 paragraphs of `dir="rtl"` take 527 ms in Chromium and 486 ms in WebKit (in `dir="ltr"` 475 / 403 ms; before, WebKit ran past the budget), 1,000 short right-to-left paragraphs with a direction mark 219 / 183 ms. **What still runs at or past the budget, with numbers:** one line of 3,000 words that does not wrap, in `dir="rtl"`, takes 3.0 s in both engines and runs past the budget in WebKit (the assistant reads nothing of the mail): it runs out of the frame on the left, where nobody can scroll, so every word is asked of the engine — the same line in `dir="ltr"` runs out on the right, where the reader scrolls, and takes 44 ms. And 5,000 short paragraphs take 2.8–3.0 s in Chromium whatever their direction (1.3–1.5 s in WebKit), at the edge of the budget. Independently of direction, 5,000 short paragraphs hold the interface for up to about 420 ms at a time in Chromium, and 3,000 buttons with a direction mark in `dir="ltr"` up to 480 ms (WebKit 305 ms) — the gate's "no task over 100 ms" holds for the gate's own mails.

**The engine's own ways (review B7-2, measured in Playwright's WebKit 2388 and Chromium, 26.11.).** In WebKit a picture in a frame without scripts loads, but its `load` event never reaches a listener outside the frame (smallest case: a `data:` picture set in such a frame; `complete` and its natural size are there after a few milliseconds, the event does not come in 1.5 s; in Chromium it comes after 1–10 ms). The pass waited for that event: in WebKit it ran into its time limit at every mail with a picture from the network and read nothing of it (closed, but every word lost), and with a `data:` picture it waited a second per width. It now asks each picture's state in step with the interface. A second finding, kept as a precaution: in WebKit a frame laid far outside the window (`left:-20000px`) on an empty page answered no hit test at all; the engine's frame there did answer in every case of the gate (one with a faint box over a word 2 000 px down, which is asked point by point), so the frame now lies in the window — invisible, behind everything, taking no click — without a case that tells the two apart. Playwright's WebKit is not the WKWebView of an iPhone or a Mac; on a device this has not run.

**When the pass cannot finish.** Where the engine is there but the pass cannot finish — the frame does not load in five seconds, lays nothing out, the budget is spent, anything throws — the assistant reads nothing of the mail (`UNREADABLE_BODY`). Only where there is no layout engine at all (a test runner) the walk's reading stands; every web view of the app has one. Appointment descriptions are read through the walk alone: they have no reader frame.
