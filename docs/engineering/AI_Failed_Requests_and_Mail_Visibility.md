# Failed AI requests and what the assistant reads of a mail

Status: 2026-11-26 (plan Umsetzung 0.9.x, B7). Two rules, each written down as a table before the code that holds it:

1. **"Nothing was sent" is a fact of the run.** The assistant withdraws a typed question and says that nothing was sent only where nothing of the run left the device (table 1).
2. **The assistant reads of a mail only what the reader shows a person** — judged by the engine of the device, at the widths that are measured, with the limits that remain (table 2).

## 1. What can leave the device in one run

A *run* is one message the user sent (or "Send again"): the context is put together, the send overview may ask, the model is called, tools may run, the run is written. **The rule:** what the app says about sending holds for the words of this request — from typing to the end of its run — and for every way out of the device, not only the models' egress.

The table starts from the transports: every way the AI side of the app has out of the device. The AI session reaches the shell only through its hosts (`AiSessionHost`, `AiMcpHost`, `AiVaultHost` in `aiSession.ts` and `mcpSession.ts`); every member of them is either one of these transports or stays on the device, and `apps/desktop/src/ai/aiEgressOneWay.test.ts` fails where a member is added that this table does not name.

| Transport | Host member | Where it is used | Can it carry the user's words before a typed run asks its model? | In the run's list (`departedTo`) as |
|---|---|---|---|---|
| Model egress (chat, search model, reader without tools, a page's processing, transcription) | `AiSessionHost.egress` → the session's `this.out` | a run hands its own egress (`runDepartures`) to every request it makes: `runAgent`, `createPrivateDataExecutor`, `createWebExecutor`, and the question's way to a search model (`contextOf` → `candidates` → `gatherCandidates` → `semanticCandidates` → `rankedSearch` → `embed` → `send`) | **yes**: the question embedded for a cloud search model | the endpoint id (`openai`, `custom-1`) |
| Model egress outside a run | the same | the notes' own embedding (`LocalEmbeddings` scheduler), a connection test or model list (`testProvider`), the context preview (`previewContext`, which may send nothing: `deviceOnlyEgress` refuses every request off the device), a transcription, a gist | no (none is a run of a typed question) | — (counts for no run) |
| Foreign servers (MCP): a prompt with the user's arguments, the answers to a server's questions | `AiSessionHost.mcp` → `AiMcpHost.native` (`mcp.prompt`) | `startMcpPrompt`, `sendMcpPrompt`: before the run | **yes**: the arguments, the answers | `mcp:<server id>`, from the run's start (`send(text, { server })`); such a run is never a typed question |
| Foreign servers: a tool call, its questions | the same (`mcp.call`) | `createMcpExecutor` in `runMessage` | no: only after a model answered | `mcp:<server id>` (`run.note`) |
| Foreign servers: listing their tools and prompts, checking them, their sign-in page | the same (`manifests`, `check`, `servers`), `AiMcpHost.browser`, `AiMcpHost.openPage` | the conversation's start, the settings | no: nothing of the user's | — |
| The internet: reading a page, a web search | `AiSessionHost.web` (`ai_web.rs`, `AiWebPlugin`); a search goes through the model egress | `createWebExecutor` | no: only after a model answered | `web` (`notingFetcher`) |
| The mail server: `search_mail`, `read_mail` | `AiVaultHost.tools` (the shells' mail clients) | the vault's tools in `runMessage` (`notingExecutor`) | no: only after a model answered | `mail` |
| External agents (ACP) | `AiSessionHost.acp`, `AiVaultHost.agents` | a conversation of their own with another maker's program | not part of a typed run: never withdrawn, never "nothing was sent" | — |
| Scripts | `AiSessionHost.scripts` | a closed box on the device; what a script calls are the conversation's tools above | no | (their tools' rows) |
| The calendar | `AiVaultHost.tools` (`get_calendar`, `get_event`) | read from the device's store (`pim.cache`) | no: nothing leaves | — |
| Everything else of the hosts (settings, stores, the index, the vault's files, replies written into a note) | the remaining members | on the device | no | — |

**The fact.** Each run gets its own list (`runDepartures` in `aiSession.ts`): a run of a server's prompt starts with that server in it; the run's egress — the session's, wrapped by `departingEgress` — adds every model request to a recipient that is not on this device, unless the egress answered it "never sent" (a refusal of the first class, `failureClassOf`) before anything came back; a request that throws, is cancelled, or ends in any other way counts; a foreign server's tool call, a page fetch and a mail search add themselves where the run takes them (`run.note`). The run hands its egress explicitly to every request it makes — nothing reaches it through a state of the session ("the run under way"); two runs of a message never run at once in a session (`send`, `replyInThread`, `runRoutine` say "busy"), and should they, each would count only its own. The turn of a typed question is withdrawn only where the list stayed empty; what the device sends for anything else at the same time counts for no run. The question's embedding goes out in a request of its own, never in a batch with the notes' embedding, and is never taken from a store of earlier questions (`rankedSearch` embeds each question anew).

**Before the model call**, the list of a typed run can hold at most one entry: the provider of the search model (requests to it are one entry however often they are repeated). A run of a server's prompt holds that server, and the search model's provider where its text went to the search; such a run is never withdrawn.

**The guard.** `apps/desktop/src/ai/aiEgressOneWay.test.ts` reads the sources: the desktop's `ai_http` is called in its egress alone, the phone's `AiNet` plugin is reached in its egress alone, each shell makes its egress once and hands it to `new AiSession`, the session takes it in one place, behind the device's switch. Inside `runMessage` and `execute` no other egress than the run's is named; every `execute` is handed a run's list; the question's way to a search model hands the run's egress on at each step; every member of the session's hosts is named in this table. The types hold the search's way too: `candidates`, `gatherCandidates` and `semanticCandidates` cannot be called without an egress.

**When the model call never went but something left before it.** The turn stays (second class: "Send again" in place), the notice names no "nothing was sent": a refusal whose words say so (`too_large`, `invalid_request`, `window_too_small`, `local_only`) is shown as `errors.somethingWentWrong` until a text of its own is decided; `unreachable` says "Could not reach …" (`ai.error.offline`), `no_key` and `unknown_endpoint` say what they say (none of them claims nothing was sent). The endpoints this run reached are kept with the notice (`departedTo`): before the model call only the search model's provider can be among them (the one way out before it that carries the user's words, table above).

## 2. What the person sees in the mail reader, and what the engine measures

**The rule:** the measurement takes the reader as its measure, not the mail's source. For whatever the reader takes only from the loaded picture, the largest the reader allows holds.

The walk over the reader's tree (`htmlVisibleText.ts`) leaves out what an element hides by its own style. What only the place of other boxes hides is asked of the engine (`engineVisibility.ts`). The engine's frame is built by the reader's own builder (`buildMailFrameDoc`), with the reader's rules for pictures from one source (`MAIL_IMAGE_RULES` in `mailSanitize.ts`); a test holds that both frames take them from there.

| What decides what the person sees | Desktop | Phone / tablet | What the engine measures | Where it differs, what follows |
|---|---|---|---|---|
| Width of the reader | the frame is `width:100%` of the mail column (`mail.css`), any width; fitted (`applyFrameFit`) | the screen's width (portrait, landscape, split view, tablet), fitted with `growHeight` | 343 and 760 px, and the widths the readers of this device show mails in (`mailReaderWidths`): every reader frame on screen in this window (two mail panes side by side), then the latest widths kept on the device by any window within 30 days, at most three (`READER_WIDTHS_MEASURED`); noted at every fit by `MailView.tsx` and `MailMessageScreen.tsx` — before any mail was shown, the window's width | **Limit:** a width the person chooses later (a wider column, rotating the phone) can show differently from what the assistant read; before the first mail the window's width stands in for the column, which may be narrower. Named in the guide. |
| Height | the frame has its own height and scrolls | the frame grows (`growHeight`) | the frame grows (`growHeight`) | scrolling inside the desktop frame reaches every line the grown frame shows: a word below the fold is reached by scrolling; nothing is clipped by the frame's height (the frame scrolls, `overflow` stays the document's). |
| Pictures from the network | shown after the person's choice (per message or always) | the same | never loaded; where the reader leaves a size to the picture, it is measured **as large as the reader allows** (see below) | see "remote pictures" |
| Dark mode / the theme's canvas | the theme's colours only for a mail that sets none | the same | the white sheet | colours decide contrast, which the walk judges; the engine judges covering, which colours do not change |
| Font size, zoom | the app's zoom scales the window; the mail's own sizes stand | the system's text size does not reach the frame | the frame's own sizes | the app's zoom scales everything alike, nothing comes to lie over anything else |
| Text direction overrides (U+202D, U+202E, `<bdo>`, `unicode-bidi: bidi-override`) | drawn mirrored | the same | the text under the override is found | it is not read (see below); right-to-left text, embeddings (U+202A, U+202B) and isolates (U+2066–2069) are no override and are read |
| The engine the measurement runs in (WebKit on iPhone, iPad and the Mac; Chromium/WebView2 elsewhere) | — | — | the frame is laid out by the device's own engine; the pass asks each picture's own state (`complete`), never its `load` event, and lies in the window, invisible | see "the engine's own ways" below |
| Words turned around without an override (U+200F, embeddings, isolates, `dir="rtl"`) | drawn in another order | the same | two words of a left-to-right script on one line, no right-to-left letter between them, the later drawn before the earlier | both are not read (see below) |

**Remote pictures.** The engine loads nothing from the network. Which of a picture's sizes the reader fixes is not read from its markup — an attribute, a word in its style — but asked of the layout under the reader's rules: in the engine's frame each picture from the network is shown, in turn, with stand-ins of 1 × 1, 1 × 4000 and 4000 × 1 pixels (`remotePictureFreedom`). A width or height that changes between them is the picture's to set, as `height:auto`, `min-height`, a `height` attribute under the reader's `height:auto`, or no size at all leave it; such a size is then made as large as the reader allows: the width 100 % of its box, the height that of the whole mail laid out — `max-width` and `max-height` still bound them, as they would bound the loaded picture. A size that stays the same is the mail's and stays (a picture of `width:300px;height:4px` keeps it, in the reader too). That is as large as a picture can be where it can cover anything: a picture in the flow covers only words that run into it from before it — whatever follows it is pushed below it —, and nothing that runs out of an earlier box reaches further down than the mail itself. The gate loads a tall picture in the reader for every such form and holds that the assistant reads only words the pixel judge sees with the pictures and without them.

**Cost.** Each text is first asked as a whole; only a text that meets something that paints, a later text, a clipping edge or the frame's edge is asked word by word. Every step of the pass — the boxes that paint, the texts, the words — asks for the interface's turn once 12 ms have passed, through a message task, which an engine does not throttle in a hidden or minimised window as it throttles timers (**limit:** a mail of thousands of painting boxes still holds the interface for one task of about 150 ms while its texts are gathered, cause not found yet — `Performance_Notes.md`); the pass has a budget of 3 seconds for a mail; past the budget the assistant reads nothing of the mail and is told that it was too long to check in time (`TOO_LONG_TO_CHECK_BODY`, not the notice for a message that cannot be shown safely). The budget is chosen from the measurement in `Performance_Notes.md` ("The mail engine pass for the assistant"); not measured on a real phone.

**Direction overrides.** A direction override (U+202D, U+202E up to U+202C, `<bdo>`, `unicode-bidi: bidi-override`) draws the letters in the order they are written whatever their direction: a person sees them mirrored, a machine reads them plainly — a known way to show text that only a machine reads. Its text is blanked for the assistant. Right-to-left mail does not use it: Arabic and Hebrew run through the bidirectional algorithm, `dir="rtl"`, embeddings and isolates, none of which is an override; the gate holds that such mails keep every word.

**Words turned around without an override.** An isolate or an embedding with an invisible right-to-left mark (U+2067 … U+2069, U+202B … U+202C with U+200F), or a mark in a `dir="rtl"` box, can turn two Latin words around on screen: a person reads "SECOND FIRST", the text says "FIRST SECOND". Where a text has such a mark, or stands in a box with a direction of its own, the engine compares the order of its words with their places: two words of a left-to-right script on one line, with no letter of a right-to-left script between them, the later drawn before the earlier — both are left out, as under an override. Right-to-left text keeps its order and is read, and so does a Latin name inside a Hebrew or Arabic sentence (its words stay in order among themselves). **Limits:** the comparison runs within one text node; words turned around across separate elements (`<bdi>` beside `<bdi>`) are not caught. "Left to right" means Latin, Greek and Cyrillic letters; numbers alone, which the bidirectional algorithm orders by their surroundings, do not count.

**The engine's own ways (review B7-2, measured in Playwright's WebKit 2388 and Chromium, 26.11.).** In WebKit a picture in a frame without scripts loads, but its `load` event never reaches a listener outside the frame (smallest case: a `data:` picture set in such a frame; `complete` and its natural size are there after a few milliseconds, the event does not come in 1.5 s; in Chromium it comes after 1–10 ms). The pass waited for that event: in WebKit it ran into its time limit at every mail with a picture from the network and read nothing of it (closed, but every word lost), and with a `data:` picture it waited a second per width. It now asks each picture's state in step with the interface. A second finding, kept as a precaution: in WebKit a frame laid far outside the window (`left:-20000px`) on an empty page answered no hit test at all; the engine's frame there did answer in every case of the gate (one with a faint box over a word 2 000 px down, which is asked point by point), so the frame now lies in the window — invisible, behind everything, taking no click — without a case that tells the two apart. Playwright's WebKit is not the WKWebView of an iPhone or a Mac; on a device this has not run.

**When the pass cannot finish.** Where the engine is there but the pass cannot finish — the frame does not load in five seconds, lays nothing out, the budget is spent, anything throws — the assistant reads nothing of the mail (`UNREADABLE_BODY`). Only where there is no layout engine at all (a test runner) the walk's reading stands; every web view of the app has one. Appointment descriptions are read through the walk alone: they have no reader frame.
