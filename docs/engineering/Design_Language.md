# Plainva Design Language ("Plainva UI 2.0")

Last reviewed: 2026-07-19 · Plan: full design-language migration of 2026-07-19 (internal planning document, maintainer workspace)

This document is the binding contract for all visible UI in `apps/desktop`, `apps/mobile` and the shared `packages/ui` layer. It complements `docs/engineering/Theme_Platform.md` (theme axes, structural rules). The visual companion is `docs/engineering/design-styleguide.html` — open it in a browser to SEE every element in light and dark.

**Enforcement is mechanical, not aspirational:** `apps/desktop/src/designLint.test.ts` fails the commit for any raw value (radius/color/font-size/z-index/shadow/duration/`title=`/legacy class/JS hover/icon literal) outside a small, justified budget, and `apps/desktop/src/designGuards.test.ts` fails it for referenced-but-undefined classes, duplicated selectors, unthemed surfaces, a property declared twice in one block, a `var()` nothing declares, a tap target under 44px and a mobile surface painting a literal. `apps/mobile/src/mobileLint.test.ts` is the mobile twin and runs the same rule set. All three run in pre-commit, pre-push and CI.

## Core character

**A calm workbench.** Clear surfaces instead of stacked borders; the accent (petrol in the default theme) carries meaning — primary action, selection, today — and is not decoration. Soft but disciplined rounding, a 4px grid, subtle chrome: the note's content is the star. Themes bend tokens plus theme-scoped class rules only; components never change for a theme.

## Scales

- **Spacing:** `--space-1..8` (4/8/12/16/20/24/32px). Chrome paddings, margins and gaps come from this scale; free pixel values only for micro details (1-2px).
- **Type (chrome):** `--text-xs` 11 / `--text-sm` 12 / `--text-ui` 13 / `--text-md` 14 / `--text-lg` 16 / `--text-headline` 22 / `--text-display` 32. Document content (editor/read mode) sizes with `em` relative to `--font-content` — `em` is the ONE sanctioned way to size content-relative text; px/rem font literals fail the lint.
- **Control heights:** `--control-sm` 24 / `--control-md` 28 / `--control-lg` 34. Buttons, inputs and selects on the same row share the same height.
- **Field metric (E10):** the FORM standard is `--control-lg` with a 12px inset (`.pv-field`); the compact role (`.pv-field--compact`, 28px) is reserved for toolbars, the sidebar search and inline cell editors. Density compresses `--control-*` globally, so compact density still reaches every form.
- **Touch heights (mobile):** `--touch-sm` 44 / `--touch-md` 48 / `--touch-row` 56. No mobile tap target below 44px.
- **Icons:** lucide sizes come ONLY from the shared roles in `packages/ui/src/lib/iconSizes.ts` — `ICON.meta` 12, `ICON.ui` 15, `ICON.head` 18, `ICON.touch` 22, `ICON.empty` 28, plus `ICON_DOC_HEADER` 44 for the document-header glyph (`--doc-header-icon` in CSS). `size={<number>}` literals fail the lint.
- **Density:** `data-density="compact"` on `<html>` compresses `--control-*`, `--pad-row-y`, `--pad-cell` and the chrome type scale. Content typography is not a density concern.
- **Elevation:** `--shadow-1` (cards at rest), `--shadow-2` (menus/popovers/floating windows), `--shadow-3` (modals). Black themes set them to `none` — there the border separates. Literal shadow recipes fail the lint.
- **Translucency (mobile rework N8):** exactly ONE surface floats over content and reads through it — the navigation capsule. `--surface-glass` derives from the theme's own `--surface-container` (`color-mix` to 82%), so every token theme gets it without naming anything, and `--glass-blur` carries the backdrop radius. A theme whose material is opaque by definition pins both back (LCARS and Win95 do: Okuda panels and 3D bevels have no glass), which is why this is a token pair and not a hard rgba. Nothing else in either shell uses translucency; a second one needs a reason in this file first.
- **Z layers:** `--z-popover` 500 < `--z-modal` 1000 < `--z-menu` 1100 < `--z-dialog` 1250 < `--z-toast` 1300 < `--z-tooltip` 1400 (drag ghosts ride the tooltip layer via `.pv-fixed-ghost`). Mobile: `--z-m-bar` 30 < `--z-m-sheet` 40 < `--z-m-sheet-dialog` 50 < `--z-m-overlay` 60. No free z-index values; purely local stacking inside one positioned container is the only budgeted exception.
- **Motion:** `--dur-1` 120ms (hover/opacity), `--dur-2` 180ms (panels), `--dur-3` 260ms (large moves) with `--ease-1`/`--ease-spatial`. Continuous indicator cycles use `--dur-spin`/`--dur-progress` and are deliberately NOT zeroed by reduced motion (a 0.01ms cycle strobes). Literal durations fail the lint.

## Radius roles

`--radius-xs` 4 / `sm` 8 / `md` 12 / `lg` 16 / `xl` 20 / `pill`. The ROLE is binding:

| Role | Token |
|---|---|
| Controls (buttons, inputs, selects, menu items, tabs, tree rows) | `--radius-md` |
| Floating menus/popovers/pickers | `--radius-md` |
| Cards and panes (board/gallery/list/empty state) and FAB | `--radius-lg` |
| Modals, peek/floating windows and bottom sheets | `--radius-xl` (mobile sheets: `--radius-sheet`) |
| Chips, switches, segmented controls, counter badges | `--radius-pill` |

Mnemonic: *control & floating = md, card = lg, dialog/sheet = xl, round = pill.* LCARS/Win95 pin the whole scale (pills / 0). Geometric radii (`50%` circles, 1-2px micro details) remain literal.

## ONE state system

- Hover: `--state-hover` (press: `--state-press`) via CSS `:hover` — never `onMouseOver`/`onMouseOut` style mutation (fails the lint), never a second hover variable family.
- Active/selected rows and toggles: ALWAYS the `--accent-container` fill + `--on-accent-container` text PAIR at weight 600 (`.is-active`, `.pv-popover-row-active`, `aria-selected` rules) — never the fill with `--accent-color` or an inherited text color on top (under Win95 the container is solid navy; unpaired text vanishes). Multi-tone row content (subtitle/time lines) switches to `color: inherit` with opacity steps while selected. The accent EDGE marker is exclusive to the file tree. `--bg-active` is CONTENT-highlight tint only (editor match/active line) — never a chrome active state.
- Focus: the global `:focus-visible` ring plus `--state-focus`; composite fields (`.pv-chipfield`, `.pv-searchfield`, palette input rows, popover search rows) light up via `:focus-within` ONLY — their inner input suppresses the global ring (see the "composite fields" block in ui.css), otherwise it reads as a second field frame. Components never set `outline: none` on standalone focusables.

## Status colors

`--error-*`, `--warning-*`, `--success-*`, `--info-*`, each with `-bg/-border/-text`. Toasts, banners, dialog kinds, sync/backup states use exclusively these; no freely chosen reds/yellows. Diff tints derive from them via `color-mix`.

## Component primitives (`packages/ui/src/components/ui/`)

Database property configuration: each visible property uses two stacked rows. The first keeps the drag/reorder controls, a wrapping property name and edit/visibility actions together; type, relation and coverage badges wrap below the name. The second labels the shared **ColumnSummarySelect** as **Summary** and gives its Select the full available width. Its accessible name includes the property name. Unknown custom summary names stay selectable and are preserved. Desktop panels and mobile sheets use the same summary vocabulary and shared **ColumnSummaryRow** over the filtered rows. This is a layout arrangement inside existing cards/sheets, with no new painted surface; their LCARS/Win95 docking and the Select's existing theme rules apply unchanged.

Database metadata filters reuse the Select primitive and the shared filter catalog. Header colours show a swatch and their stored colour value, document icons show the actual glyph and stored name, and tags show complete values. A pinboard's custom label source is named in the property label. Suggested values come from the unfiltered source and retain an active value even after it disappears; an empty result never removes the way to change the filter. These pickers use existing Select theme docking and add no new painted surface.

Button (primary/tonal/secondary/ghost/danger/danger-soft — **Cancel is always ghost**), IconButton (`.pv-iconbtn`; `.is-active` is the one toggle idiom), Field family (TextInput/SelectField/TextArea with the `compact` role), **Select** (field-metric trigger + popover-contract panel, accent-container selection, search row from 8 options; forms, dialogs and toolbar filters use this primitive. A native `<select>` is allowed ONLY wearing the field skin `pv-field pv-field--select` — the documented idiom for dense tool rows whose popup may stay OS-rendered, like the native date/time/color inputs; a naked `<select>` fails the `nakedSelect` lint rule), **SearchField** (THE search pattern: magnifier sibling, clear-X, Escape clears first / closes second; `className` AND `style` address the FIELD — every other prop belongs to the inner input, so a caller can lay the field out in a flex row and the field may shrink, `min-width: 0`), Checkbox/Switch/**Radio**, Segmented, MenuSurface/MenuItem, Modal (icon slot, `headerNote` — one quiet line of context between the title and the X, such as where the thing being made will land — `testId`), **Banner** (info/warning/error/success notice strip), **FloatingWindow** (drag/resize/session-persist chrome shared by the peek preview and mail compose; `.pv-peek-head` is a themed surface), Fab (`.pv-fab` — the mobile floating buttons render it with position-only `.m-fab-float` modifiers), EmptyState, TooltipHost, ToastHost, DockedToolbar, **SelectionBar** (the count-and-actions strip a multi-selection puts in place of a toolbar).

Sync state has THREE colours, not two: idle/`syncing` neutral, `retrying` neutral with a muted glyph, `error` in `--error-text`. `retrying` is a temporary failure the worker expects to survive — a dropped request, a 503, a token caught mid-rotation — and it is neutral on purpose: red is reserved for something that needs a person. The core reports the state and the wall clock of the next attempt; the sentence ("no connection — trying again at 14:05") is built in the shell, which is the only side that has language. The raw provider string stays in diagnostics and the error history (mobile rework round 3).

Chips: `.pv-chip` is 22px with symmetric `0 10px` padding and `gap: 6px`; removable chips (`.pv-chip--removable`) use `0 4px 0 10px` and keep their own 4px gap for the X; count badges (`.pv-badge`) are 18px, min-width 18, `tabular-nums`. A leading icon goes through the `icon` prop into `.pv-chip-icon`, a sibling BEFORE the text span — never a child of it. As a child it joined the label's `text-overflow` chain, and with no gap on `.pv-chip` it touched the first letter at a measured 0px (mobile rework round 3; the vertical centring measured fine either way — the collision alone is what reads as misaligned). **Component inner metrics live ONLY in ui.css** — call sites never re-specify paddings. The OKF lifecycle badge (OKF 0.2, plan P3a) is a `.pv-chip pv-chip--sm` in the document header — `draft` on the neutral chip, `deprecated` with `.pv-chip--danger` (the `--error-*` trio; the only danger-toned chip). `stable` and an absent status stay silent, and a task database's `status` column never becomes a badge — the shared `trustBadgeOf` decides for the live widget, the read view and the phone alike. The stale notice is the **Banner** primitive (warning) with exactly one action, "Open properties"; the trust section in the properties panel uses the same chips for the trust level (accent-container pair = reviewed by a person, plain = machine-confirmed, `--muted` = not verified). The trust section carries exactly ONE action, **Mark as reviewed** (plan P3b): a `ghost`/`sm` button with the check glyph on the desktop, an action row in the phone's context sheet. It appends `human:<name>` with the current instant to `verified`, asks for the name once per vault and keeps it on the device (a per-vault setting, deliberately outside the profile catalogue). `generated` and `sources` are written only by the machine paths — import, mail capture, task sync — with `plainva-<producer>/<version>` actors; the editor never stamps a trust family, and existing notes are never stamped after the fact.

Tags (finding 2026-09-19): a tag has ONE look wherever it stands in running text — **`.pv-tag-pill`**, the chip-tag pair (`--chip-tag-bg`/`--chip-tag-fg`) on `--radius-pill`, sized in `em` because it sits in note text of any size, the path of a nested tag quieter in `.pv-tag-parent`. The live editor draws it as a MARK (the text stays `#project/website`, the caret walks through it), the reading view and the rendered table cell as a span; all three read the index's rule (`core/tagRule.ts`), so a pill never marks what the tag pane cannot list. Every surface that draws a tag — the pill, the property chip, the desktop's table cell, the pinboard label — carries `data-tag-color`, the slot hashed from the tag's ROOT (`tagColorIndex`, slots 1–7: the grey slot 0 is never dealt); the glyph in the tag lists carries the same slot as `data-tag-ink`. The slot paints ONLY under `html[data-tag-colors="on"]`, the device switch **Colour tags** (Appearance, off by default, stored with density and fonts, never in a note): a calm note stays calm until somebody asks for colour. A surface therefore never colours a tag itself and never sets an inline colour on one — an inline colour beats the switch (that is why the desktop pinboard's tag label became the class `.pv-pinboard-tag`). LCARS keeps the pill hollow with the hue as ink; Win95 squares it.

The note body (finding 2026-09-19) — three things the note draws the same way while it is written and while it is read. **Callout = one card** in both modes: a 1px line in the callout's colour, its tint, `--radius-md`, the title in the colour, no bar and no glow (a glow on many blocks is noise on a phone, and it does not print). The live editor has no block element to put a border on, so the card is built from LINES: every line of the callout carries `.cm-callout` with the side lines and the tint, the first adds `.cm-callout--first` (top line, top corners), the last `.cm-callout--last`; a one-line callout carries both. The strength is two tokens per MODE, not per theme — `--callout-fill` (10 % light, 16 % dark) and `--callout-line` (42 % / 55 %) — because a fixed 8 % of a colour chosen for a light ground barely shows on a dark one; the `--callout-<key>-tint` tokens are derived from them and stay a theme's override hook. The fill is mixed with `transparent`, never with the page colour: an opaque line background would hide the selection behind it. A plain blockquote keeps its bar. **A done task** reads like one everywhere: text in `--text-muted`, struck through, in the note as in the task view, the board checklist and the note cards; the box itself stays as it is, and an open task stays in text colour (red means danger in Plainva, not "to do"). **Indent guides**: from the second list level on, a hairline in `--border-color` under each parent bullet — drawn as a BACKGROUND of the line (`.cm-list-guides-N`), so there is no extra DOM, nothing to select and nothing for the caret to land in; the reading view draws the same line as the border of a nested list. Always on, no setting.

Colour choice (plan "Farbwahl überall", 2026-09-04): ONE grammar wherever a colour is chosen — **SwatchGrid** (`.pv-swatches` / `.pv-swatch`): `--control-md` discs in fixed slots (`--swatch-cols`: 8 on settings pages, where the 300px control column holds them; 6 in popovers, where ten tones plus the free disc make two rows), the pick an outline ring on `--text-main` — never a check glyph, it vanished on white —, an optional "none" slot FIRST (`.pv-swatch--none`: the letter A for "default tint", a struck disc for "calendar colour") and the free colour LAST (`.pv-swatch--free`: a hue ring around the current value with the native colour input invisible on top, so the OS picker opens from the disc; it wears the ring whenever the value is none of the presets, so the ring always sits somewhere). A single disc is the **Swatch** primitive — also the toolbar affordance that opens a grid. Desktop popovers are **ColorPopover** (grid plus optional remove; a tone applies AND closes, the free disc applies and stays open — a change event from the OS colour dialog is not an outside click). The phone renders the same vocabulary in touch size (`MobileSwatchGrid`: `.m-colorgrid` with `-free` and `-none` tiles). The values are DATA (`ACCENT_PALETTE`, `EVENT_COLOR_PALETTE`, the custom-theme presets); the event palette deliberately offers no free disc, because event colours map onto provider colour ids and a free value would not round-trip. Before this there were five forms: rectangles plus an apply button in the header popover, flat rectangles plus a chip in the icon tint, a naked colour field in the image toolbar, 20px mini discs at the event, and a grid plus an extra row on the phone.

Date jump (plan Kalender, Anker-Links, Dependabot 2026-09-10, P1): ONE grid wherever a person picks a date to go to — **DateJumpPicker** (`.pv-datejump`): a year row with double chevrons, a 4×3 month grid (`.pv-datejump-month`, the shown month on the accent-container pair), a 7-column day grid (`.pv-datejump-day`: the selection filled on `--accent-color`, today as an inset ring, the caller's current range as a band on the accent-container pair, a marked day — daily note, entry — as a dot) with the week starting where the setting says and an optional ISO-week column on Monday-first grids, and a foot with the keyboard hint and an optional tonal **Today**. Month and weekday names come from `Intl` in the app language, never from literals. The grid is ONE Tab stop: the arrow keys move a day or a week, PageUp/PageDown a month (with Shift a year), Home/End to the week's ends, Enter picks, T is today, Escape closes (roving tabindex). `--sheet` raises the rows to `--touch-sm` for the phone. The control that opens it is **DateJumpTrigger** (`.pv-datejump-trigger`): the period label with a small chevron, `aria-haspopup="dialog"`, and the accent-container pair while the popover is up — the calendar tab's title, the sidebar calendar's month name and the database calendar's title are the same control. The desktop hull is **DateJumpPopover** (`.pv-popover.pv-datejump-pop`, the popover contract widened to 300px with a click catcher); the phone's hull is a bottom sheet. Before this there were three hand-built grids — the sidebar's inline popover, `CustomDatePicker` with German weekday literals in every language and Monday hard-wired, and none at all in the calendar tab, whose title was plain text.

Event description (plan Befunde 24.09., E25): the description of a calendar event is FOREIGN text — whoever sent the invitation wrote it — and both previews (the desktop's floating window, the phone's sheet) draw it through ONE component, **EventDescription** (`.pv-evtdesc`), from the linear parser in `pim/eventDescription.ts`; never as HTML and never through `markdownToHtml`. It sits in a quiet box on `--bg-secondary`. A link is a chip (`.pv-evtdesc__link`: `--radius-xs`, a hairline on `--border-color`, `--bg-primary`, the accent as text) that names the HOST it leads to behind a link glyph — Outlook's addresses are pages of percent-encoding, and a host is what a person can judge; a link with words of its own shows them, with the host in `--text-faint` beside them. Only http(s) becomes a chip; the full destination is its `data-tip`. A Microsoft Safe Link names the host of its TARGET and gets a quiet line under the chip (`.pv-evtdesc__via`, "via Microsoft Safe Links") — but what opens is always the original address: the check the organisation put in front of the target is not the app's to skip. The meeting's own join link (`meetingUrl`) is **EventJoinButton**: a primary `Button` with a video glyph under the time, named after the service when its host says which one it is ("Join · Teams"), `sm` in the window, `md` on the phone. Docking: tokens only; the chip and the box are exempt from theme rules of their own, the button is a `.pv-btn`.

Cloud-account patterns (settings): an account row (`.pv-acct`) = provider monogram + identity + service chips inside a `SettingCard`. The monogram (`.pv-acct-mark` + `--<family>` modifier) paints exclusively from the themed `--chip-*` slots; service chips (`.pv-svcchip`) are 22px pills on the accent-container PAIR. The connect wizard is built from provider tiles (`.pv-provtile` — card-radius surfaces; selected = accent-container pair, themed for LCARS/Win95), a numbered step header (`.pv-wizsteps`/`.pv-wizstep`; the active step number is a primary-accent disc, done steps use the accent-container pair) and per-service check/status rows (`.pv-svcline`, `.pv-svcstat` — the setrow grammar with a leading icon; status rows report success, waiting AND error states). Both stack their text: label and sub sit in a `-main` column with `min-width: 0`, the row aligns to `flex-start`, and the sub wraps. The status sub carries a PROVIDER SENTENCE, so a centred single line without shrink allowance painted the error straight through the service name (2026-08-19) — a row that can hold a sentence gets a line of its own. With the provider catalog (stage A+, 2026-07-20) the tile wall lists 17 providers sorted by real-world reach (generic mechanics last), topped by a SearchField that also matches IMAP-preset providers; a preset hit surfaces the mail tile with a muted subtitle line (`.pv-provtile-hint`). Provider auth hints (app password / authorization code / separate mail password / enable-IMAP-first) render as SettingCardNote lines with a `.pv-linkbtn` to the provider's official guide — data from the catalog, never per-provider markup.

Mobile app bar (S11): ONE header for every surface — `.m-appbar` with `.m-appbar-row` (back · `.m-appbar-ttl` with `h1` plus optional `.m-appbar-sub` · `.m-headactions`), and `--lg` as the single difference a tab root makes. It is sticky and doubles as the status-bar scrim (full-bleed, top safe-area inset), flat at rest and raised (`.is-scrolled`) once content passes under it — M3 scroll elevation. The phone had TWO header families with different size, weight, edge and elevation, so every step inward changed all four at once; a third, `.m-topbar`, carried the scroll elevation and was referenced nowhere. Two rules hold it together (`mobileLint`): no surface writes its own `<header>`, and no `⋮` opens the app settings — a three-dot menu means actions on the object that is open, everywhere. Reading downwards, the navigation bar draws back to its icons (`.m-tabbar.is-away`); the app bar publishes the direction because it is the piece that can see the scrolling element.

Bars & areas list (settings, 2026-07-28): one ordered list per bar inside a `SettingCard`. `.pv-setcard` carries NO padding of its own — `.pv-setrow` supplies the inset — so anything placed in a card directly must bring the row inset itself, or it sits on the card edge. The family: `.pv-barlabel` (VISIBLE / HIDDEN group heading), `.pv-barrow` (grip + area icon + label + optional hint + eye; `is-over` paints the reserved 2px top border as the drop indicator, `is-dragging` dims the lifted row), `.pv-barrow-grip` / `.pv-barrow-icon` / `.pv-barrow-label` / `.pv-barrow-hint`, and `.pv-barfoot` for the inherit line plus the default actions. The rows are DENSER than a `.pv-setrow` on purpose: this is a list of up to ten entries being arranged, not a stack of single settings. Every row shows the glyph the surface itself shows — the icon lives in the bar model (`BarAreaDef.icon`) next to the label key, so the settings list can be read against the interface instead of translated back from names. Since S10 the model also carries the PHONE's navigation bar (`mobileBar`), which is what makes that bar arrangeable from the desktop and lets it travel in the settings profile; its last entry, "Areas", is deliberately outside the model, like the rail's Help and Settings — a way to everything else that a user can hide is not a way back.

Cascade deletion dialog (plan Kaskadenloeschung, 2026-07-21): ONE danger dialog rendered from a precomputed deletion plan (shared kernel `packages/ui/src/base/deletionPlan.ts`). It reuses the quiet-cards grammar — `.pv-setgroup` labels over `.pv-setcard` cards ("Wird gelöscht" card without a checkbox, one card per assigned/db-items/linked-database group, an "Aufräumen" card) — plus the cascade family: `.pv-cascade` (modal body stack, layout only), `.pv-cascade-row` (group row: Checkbox primitive + label/description + `.pv-cascade-count` pill on the accent-container pair), `.pv-cascade-items` + `.pv-cascade-item` (collapsible scrollable element list on `--bg-primary`; checkbox, doc icon, title, muted path; `--sub` indents sub-elements, `.is-off` mutes excluded rows), badges `.pv-cascade-badge` (`--warn` for shared/multi-membership on the warning tokens, `--muted` for sub-element counts) and a danger-tinted step-2 row `.pv-cascade-row--danger` ("delete the whole linked database"). A linked database is NEVER prose — always its own named card ("Verknüpfte Datenbank · X"). The confirm button is `Button variant="danger"` with a LIVE file count; the existing large-deletion second prompt and the cloud/snapshot foot note stay unchanged.

Entry inspector (right sidebar “Databases” section, plan P2, 2026-07-28): the section shows the note's row THE WAY ITS DATABASE SEES IT — the column order of the first view, the declared types, option colors — and edits it through the same cell layer the table uses (`useBaseCells`), so a status changes without opening the database. One block per membership (`.pv-dbinsp-block`, separated by a hairline rule — without it the second block’s values read as a continuation of the first); a note that is a row of two databases gets two. `.pv-dbinsp-grid` is a two-column key/value grid (`.pv-kv-key` labels, `.pv-dbinsp-val` values — the value column takes the remaining width because the editors live there). `.pv-dbinsp-nav` is the position stepper (“12 / 34” in `.pv-dbinsp-pos`, tabular numerals, IconButtons to either neighbour) — a pill on `--surface-container-low`, squared off under LCARS, a sunken well under Win95. It appears only when the note is IN the view: membership deliberately ignores view filters, so “0 / 34” is a state that can occur and must not be printed. `.pv-dbinsp-disclose` is the collapsible sub-items header (chevron + `.pv-kv-key` + count badge). The properties panel is not replaced: it shows raw frontmatter, unordered and untyped.

Read-mode text selection on mobile has explicit Copy and Select all actions alongside the permitted authoring actions. The measured selection toolbar wraps within the visual viewport. It owns the context menu for selected text inside that reader, so a second native callout cannot cover its actions; native selection handles remain available. Desktop uses its own reader context menu, as recorded in the parity catalog. Editable text retains its normal system clipboard menu.

Selecting several rows (plan Mehrfachauswahl, 2026-08-19): a multi-selection REPLACES the surface's toolbar with `.pv-selbar` — a count on the accent-container pair, the actions it enables, and a ghost "clear" at the far end. It replaces rather than stacks because while a selection exists that is what the surface is about; a second row would also push the rows themselves down by exactly the height a person is trying to read. The bar is shared, so the mail list, the database views and anything later say "3 selected" in one voice.

WHERE the selection is grabbed differs per shell, deliberately, and the two answers are not interchangeable. On the desktop it is a checkbox column (`.pv-selcol`, ghosted until the pointer is on the row or a selection exists; the header checkbox carries the indeterminate state) — because the click on a CELL is already the inline editor, the core function of a table, and the click on a list card already opens the note. On the phone there is no pointer that hovers, so the established rule carries instead: holding a row opens its sheet, whose first NAMED entry is "select several", after which a tap toggles and the square choice mark (`ChoiceMark multiple`) marks — several at once is a box, as it is on the desktop. That rule was written on 2026-08-13 because holding used to mean two different things; unifying the two shells onto one gesture here would undo it. What IS shared is everything underneath: the same selection reducer, the same delete path, the same write path.

Security & Sharing (P3–P11 encrypted workspace): the settings page uses a compact security-centre dashboard before the detailed administration surfaces. Its `.pv-security-hero` status surface and three `.pv-security-summary-card` entries (recovery, devices, team) follow the quiet-card grammar and expose one clear next action each. A visible action is never left inert because a different vault is selected, sync is missing or the workspace is locked: activating it opens the selected vault, the connection settings, setup or unlock flow as appropriate. Only an operation that is already running or a genuinely incomplete form may disable its submit button, and the unmet requirement remains visible next to it.

Team administration is a `.pv-security-admin` master/detail surface (plan Security & Sharing UX, package B): a `.pv-navlink` rail (`.pv-security-nav`) selects ONE area — members, groups, Vault Slices, devices or publications — and `.pv-security-detail` renders only that area, so members/groups/slices are never merged into one panel. It is NOT a tablist; the rail follows the settings-navigation idiom. Narrow screens stack the rail (horizontal scroll) above the detail. Every picker (role, scope, slice, publication mode/access/provider, new owner) is the themed `Select` primitive, never a native `<select>`; roles are localized options with a one-line capability description. Slice creation is a four-step `.pv-security-slice-wizard` (details → content → permissions → review) with selectable content-type cards, a materialized preview and explicit live/sanitized publication choice. Rekeying is a risk dialog that names future-only versus full-history scope and shows durable progress. The security release gate is a status surface, not a disabled product action: automated evidence and still-required independent/manual evidence are listed separately. Where a form field would otherwise ask for a MACHINE value, a chooser takes its place (plan P5, finding B8): group membership is a `.pv-security-picker` checkbox list over the members, a selection slice is that same list over the workspace objects with a filter above it, and a dynamic slice is a `.pv-security-rule` row builder — field, comparison, value, with the value-type choice offered only where the protocol compares by type. The stored value stays reachable underneath in a `.pv-security-tech` disclosure, and anything the builder cannot express keeps that raw field as its ONLY editor instead of being silently rewritten: a picker may replace typing, never a decision somebody already made. A picker also keeps what is already selected visible while a filter narrows the list, so nothing can be lost unnoticed. Where two actions differ in their CONSEQUENCE rather than in their name, the difference is a labelled choice and not two differently coloured buttons (plan P5, finding B9): a `.pv-security-choices` radiogroup inside the dialog gives each option a bold name and the sentence that explains what it does, so the choice itself is the explanation instead of a confirmation that arrives after the click. Machine values — hex identities, key epochs, remote object keys — leave the reading line entirely and gather in ONE `.pv-security-tech` disclosure per area rather than trailing every row; they stay reachable because a support question needs them, but a sentence about a colleague is not the place for a protocol identifier. A long-running background job (a full rekey rewrites every readable object) is shown as its own card with `.pv-security-progress`, never inside a block that starts collapsed, and says that it survives a restart when its cursor is durable.

Setup uses the Modal primitive with `.pv-security-wizard`; its textual step markers use the accent-container pair only for the active step. Recovery setup is a numbered task list: save the recovery file, store the code separately, then prove the backup is readable. The code is split into visibly numbered `.pv-security-code-group` tokens and the requested tokens are highlighted, so copy never asks a person to infer what an unnumbered “group” means. The primary action remains disabled until the file was saved and both requested values match, while `.pv-security-next` always names the unmet requirement or confirms readiness. Copying is helpful but not mandatory because printing or writing the code is valid. Technical identity facts stay subordinate in a disclosure instead of interrupting the task flow. Recovery renewal and owner transfer are save-before-activate flows: the replacement recovery package is written first, only then may its anchor/policy become active. Destructive removal of legacy remote plaintext is a danger action behind the app confirmation service and is unavailable until migration is active.

Team governance reuses `SettingCard`, `SettingRow`, `Modal`, field primitives and status `Banner`s. Pairing approval always has a verification step that exposes the device fingerprint before the final action. Roles and scopes are explicit form controls; slice creation shows a local path preview before publication. Device/member revocation and a move that would remove the actor's own read access use the app confirmation service. The editor expresses Reader/Commenter state as a banner plus a hard read-only editor; comments are a compact side stack and never injected into Markdown. Integrity items expose retry/export/repair/ignore as secondary actions, while encrypted revision history keeps the existing version-history modal and writes restores as new revisions.

Rules:

- New UI builds on the primitives; no new `position: fixed` overlay outside `Modal`/`Menu`/`Toast`/`Tooltip`/`FloatingWindow` — popover panels use `pv-popover pv-popover--fixed`, invisible click catchers `.pv-click-catch`, drag ghosts `.pv-fixed-ghost`.
- The primitives render shared `pv-*` classes (styles in `packages/ui/src/styles/ui.css`) — ONLY that way can themes restyle them. Inline styles are limited to positioning/measurements.
- Blocking system dialogs are taboo: `window.confirm/alert/prompt` and Tauri `ask/message/confirm` are replaced by `dialogService`/`toast`; only the OS folder/file pickers remain native.
- Hover hints via `data-tip` (TooltipHost), never `title=` (fails the lint); icon-only buttons additionally carry `aria-label` — `data-tip` is NOT an accessible name.

## Arrangement schemata

- Modal footers: right-aligned, ghost Cancel left of the primary action (Modal's `footer` prop). Footer actions wrap at narrow widths so every translated label stays reachable.
- Forms: label-over-field, `--space-3` row gap, one shared control height per row. A field that shows a STORED setting types into its own draft (`CommittedTextInput` / `useFieldDraft`, E23): it saves after a pause, on blur, on Enter and on unmount, normalizes only when saving, and takes over a change from elsewhere only while it does not have the focus. Bound straight to the stored value, an asynchronous save pulled the text back under the caret (the phone's "Date format", TestFlight 2026-09-22) and a normalizer like `trim() || "Daily"` refilled a cleared field mid-word; the phone's settings state is one optimistic hook (`useSettingsState`), so a slider does not snap back while its write is in flight.
- Search fields: one schema app-wide (the SearchField primitive; palette/popover search rows are the borderless in-surface variant with the same Escape contract). **A search field takes its row; the caller limits it** (finding 2026-09-24, E19). A field is a flex item with the row's free space, never one that stays as wide as its placeholder: the phone's app bar puts ANY control handed to its title slot (`titleAs`) into the same flexible holder a heading gets (`.m-appbar-ttl`), and a surface that wants a narrower field says so with a limit of its own. The phone's search page showed the opposite for seven weeks — the field ended at 60 % of the bar once a sort button stood beside it; the same class as the database search on the desktop and, before it, the graph's filter. Its placeholder names the main job first ("Search or > for commands").
- Menus: thematic groups separated by `MenuSeparator` (or the `.pv-menu-sep`/`.pv-popover-label` classes in hand-anchored menus); the danger item is ALWAYS the last group behind a separator. Homogeneous list menus (move-to-folder, link bundles) stay ungrouped by design. A menu that a keyboard walks through while the caret stays somewhere else — the `@`-mention picker is the case — marks its current row with `MenuItem active` (`.pv-menu-item.is-active`, the `--accent-container` pair, same as a selected row anywhere else) and opens with `autoFocus={false}`; the row must also swallow `mousedown`, or the click blurs the field before the pick lands.
- Tooltips carry ADDED information only: file tabs tip their vault path, virtual tabs (plainva://…) tip nothing — a tooltip must never repeat the visible label or leak internal pseudo paths.
- Narrow sidebars degrade in three NAMED steps, identical on both sides: `comfortable` (>= 280px), `compact` (232-280px), `minimal` (< 232px). `useSidebarStep` measures the panel with a ResizeObserver (one step is structural — the calendar becomes a week row — which no stylesheet can do) and writes `data-side-step` on the panel root. Surfaces react through that attribute; anything carrying a row metric re-declares the density tokens (`--tree-row-*`) instead of restyling itself, so one place decides. The hook hands out a CALLBACK ref: a panel that mounts later than the hook (the left one appears only with a vault) would otherwise be measured once as null and stay comfortable forever.
- **Adaptive shell** — three window classes and a fourth number (mobile, finding 2026-08-21).
  `windowClass.ts` publishes Material's classes on the document root: `compact` (< 600) one surface at a time, `medium` (600-839) a rail beside one surface, `expanded` (>= 840) navigator and working surface side by side. The class asks for BOTH edges — a phone in landscape clears 840 on width alone, and two columns in 400px of height is the tablet layout on a device that is not one.
  A **third** column is a separate question with its own, wider number (`DOCK_MIN` = 1024) AND the user's decision (`contextPanelDocked`, device-local, off by default). At 840 the rail, a navigator of at least 280 and a context column of at least 300 already claim 668px, and what is left is not a working surface. Below the number, or without the decision, the SAME button opens the sheet — one control, two presentations, never a feature that only exists on one size.
  **Every level of the chain sets `min-width: 0`.** A flex item's automatic minimum size is its CONTENT, and a shell hands its width DOWN: a page that may shrink inside a shell that may not still renders at the content width. The measured failure was 1131px of columns inside a 1024px window, with the page, the app bar and the title all faithfully that wide. `#root` carries `overflow-x: clip` as a safety net — `clip` rather than `hidden` because it forbids the scroll instead of offering it — but the net is not the rule: clipped content is unreachable content.
  This is watched where it is visible: `mobileLint` asserts the `min-width` on both levels, and the screenshot matrix measures `scrollWidth` against `innerWidth` at every captured surface in both tablet viewports (768x1024, 1024x768). A picture cannot show a sideways scroll — the shutter crops at the viewport — which is how a tablet shipped with every screen scrollable; and the measurement asks one level INSIDE the clip, or the net would report "fits" for exactly the layout it is hiding.
- **A finding is a group, not a row per artifact** (finding 2026-09-03, `pv-quarantine-*`). A `SettingRow` fits one setting with one control; it does not fit a diagnosis with four actions — the control column is a fixed 300px that does not wrap, so the buttons ran over the description. A list of findings groups by cause (and, where it applies, by device): title in the person's language, a meta line with count, kind, device and times, an explanation with the numbers the check knew, a "what you can do" line, and an actions row that wraps (`flex-wrap`), with the settle actions in a menu behind the danger separator. Settled groups hide behind an `Open · All` Segmented and the raw machine sentences sit behind "Show entries". Both shells render the same classes; the grouping and the text keys are shared (`groupQuarantine`, `quarantineReasonKeys`).
- Column dividers that resize (findings round P8.1): a 5px grid track, transparent until hover, `--accent-container` while dragged (`.pv-mail-grip`; the app's sidebar grips share the metric). The drag starts on **mousedown**, never pointerdown — `preventDefault()` on a pointerdown suppresses the compatibility mouse events, so a window `mousemove` listener never fires and the drag registers without doing anything. The clamp is a pure helper next to the surface, not arithmetic inside the move handler: every column keeps a minimum, and the panel the others exist for (here the reader) is the one that must never be squeezed away. Widths that a user chose are remembered PER VAULT and registered in `vaultForget`.
- **Grouped rows** — the container grammar (mobile rework N2). A run of related rows sits in ONE bordered card under a section heading, with hairlines between the rows and none after the last. The card is `padding: 0` and clips (`GroupCard`); the rows carry the padding (`RowList` + `Row`). A row is: optional icon slot (fixed width, muted), a two-line text block that truncates rather than wraps, and an optional trailing element (chevron, value or switch). An indented variant keeps the SAME height and only moves the left edge, so a hierarchy never changes the rhythm. Tinted and warning variants change the fill, never the metric.
  The section heading (`SectionLabel`) is the only heading dialect in a scrolling surface: micro caps, `--text-xs`, faint, with an optional trailing slot for a count or one action.
  Row metrics are named tokens (`--pv-row-min`, `--pv-row-pad-y/x`, `--pv-row-gap`, `--pv-row-indent`), so the ONE place that decides them is the token block and not a surface. The touch variant raises only the minimum height; nothing else differs between shells.
  This exists because it did not: the phone had NO divider rules at all and only 4 of 209 rows inside a card, while the target design uses this arrangement 42 times. Full-width button stacks are not this pattern — an action that LEADS somewhere is a row; a button remains only where something is TRIGGERED.
- **Settings page grammar** — TWO edges and ONE rhythm (mobile feedback round 2026-08-15; `.m-settings`, `SettingField`). A settings surface has exactly two left edges. The **page edge** (`--m-edge`) carries section headings, card borders, and hints that belong to a whole card. The **row edge** (page edge + `--pv-row-pad-x`) carries text INSIDE a card. Nothing sits anywhere else. The vertical rhythm belongs to the PAGE, not to the elements: the surface is a flex column with one `gap`, and no child carries its own margin.
  Both halves come from a measurement, not a preference. Three left edges stood on one screen — 14px (section heading, plain hint, field label), 28px (row text, and `.m-hint--inset`, which reproduced the row edge OUTSIDE a card), 32px (`.m-sliderrow`, a slider's caption row used as a heading, in sentence case with its own padding). And the missing gap under a field was never a forgotten margin: `.m-page` is plain block flow with no `gap`, so spacing was the sum of the children's own margins — and both a field and a card have none, which is exactly zero. The sync surfaces never had the bug because `.m-sync` was already a flex column with a gap: one app, two rhythms.
  So a **field is a row**: label as the row title, value/input beside it, an optional trailing row action (the folder browser). That removes the third edge rather than aligning it, and gives every folder setting the same browser without inventing a control. Forbidden from here on, and watched by the ratchet: an inset hint outside a card, and a slider row standing in for a heading — a heading is `SectionLabel`, in every shell.
- **Band rule** — a full-bleed hairline BETWEEN two bands of a scrolling surface (mobile rework round 2, N9.1; `.m-bandrule`). It is the counterpart to the grouped-rows hairline: that one separates rows INSIDE a card, this one separates one kind of content from another ON the page. It bleeds past the page inset to both screen edges, because a rule that stops where the text stops reads as an underline for the block above rather than as a division. It draws on `--border-color-light`, the same token every row hairline uses, so it inherits each theme's divider colour without a selector of its own. Use it once, at most, per surface: a second one turns a division into a stripe pattern. Do NOT use it under a section heading (the heading already divides), between rows (that is `RowList`), or as the last element of a surface.
- **Content row** — the grouped-rows `Row` with `wrap` (mobile rework round 2, N9.4). A settings row is ONE height because its title is a *name*: cutting "Standardkalen…" at the ellipsis loses nothing, the value beside it carries the meaning. A task, a search hit or a mail subject is the opposite — the title IS the content, and the ellipsis cuts the information. So `wrap` lets the title run to two lines (clamped, then the ellipsis) and turns the second line into a wrapping meta line for chips: state, date, tags. Everything else stays the row it was — same metric tokens, same icon column, same trailing slot. Use it where the title is content; do NOT use it to squeeze a long label into a settings list, and do not put more than one action in the trailing slot just because the row got taller. A row that carries its own controls AND still leads somewhere takes `controls`: it becomes a container with `role="button"` instead of a native one, because nested buttons are invalid HTML and the inner ones stop working — that is literally how the month grid's day cell came to have nothing clickable inside it (issue #34).
- **Row swipe** — the touch shortcut to a row's own actions (mobile; `SwipeRow` + `.m-swipe-*`). A row slides left over a tray of at most THREE slots of 66px; the destructive one is always last and wears the `--error-*` pair. The actions are **congruent with the row's action sheet** — same actions, same order, same labels, one definition reached two ways — so the gesture is a shortcut and never the only path. `touch-action: pan-y` on the front face is load-bearing, not decoration: without it the browser claims the horizontal drag for the list's own scrolling and the row never moves at all, which is exactly how a complete gesture shipped invisible for a full round. A row that is currently part of a multi-select carries no swipe: a gesture meaning exactly one row has no clear meaning beside a selection still being assembled. A row whose actions sit visibly ON it (checkbox, chips, trailing buttons) needs its SHEET first: without one there is nothing to mirror, and a swipe would invent a second definition instead of offering a second route to an existing one. The task row was the last such row, and it got its sheet in S22 — which is what made its swipe possible rather than merely desirable.
  **Findability is part of the pattern, not an afterthought.** A gesture announces itself once per vault through the shared `Banner` (info tone, a dismiss action, `.m-swipehint` above the list it describes) — no permanent grip strip on the row edge, which would be a new visual pattern for something a sentence can say once. The accent-container pair is deliberately NOT used here: it is this system's active/selected idiom, and a lasting strip in the selection colour that is not a selection weakens that meaning.
- **Sidebar blocks** — what separates two KINDS of thing is space, not another line (desktop feedback 2026-08-15). A hairline separates rows INSIDE a block; a block ends with a gap. The pinned lists ("Recently opened", Bookmarks) therefore keep hairlines between them and none after the last, and the view switch — a control, not a row of that list — sits on its own container surface (`.pv-side-switch`, `--surface-container-low` + `--radius-md`) with `--space-2` around it. Measured before the change: the switch had ZERO pixels of top padding and sat flush on the third hairline in a row, so it read as another bookmark. This is the settings-page grammar applied to a sidebar: the gap groups, the surface names, the line only divides within.
  **One left edge for file rows.** A section's rows start AFTER its disclosure control, at the header's icon — never at the chevron, which is the outermost element in the panel. Otherwise a bookmark sits further left than every row of the file tree below it and the column reads as ragged. The indent is `calc(--pv-sec-glyph + --pv-sec-gap)` on `.pv-side-section-rows`, i.e. the header's own geometry, so it follows a change of icon size or gap; the E2E asserts the ALIGNMENT (row icon == section icon == tree icon), not the pixel. The whole padding lives in that class: an inline `padding` shorthand beats a stylesheet `padding-left`, which is how the indent silently did nothing on the first attempt.
- **Sidebar blocks** — what separates two KINDS of thing is space, not another line (desktop feedback 2026-08-15). A hairline separates rows INSIDE a block; a block ends with a gap. The pinned lists ("Recently opened", Bookmarks) therefore keep hairlines between them and none after the last, and the view switch — a control, not a row of that list — sits on its own container surface (`.pv-side-switch`, `--surface-container-low` + `--radius-md`) with `--space-2` around it. Measured before the change: the switch had ZERO pixels of top padding and sat flush on the third hairline in a row, so it read as another bookmark. This is the settings-page grammar applied to a sidebar: the gap groups, the surface names, the line only divides within.
  **Three columns, and only three.** The disclosure chevron sits alone in a gutter; every icon — a section's own, a pinned row's, a tree row's — sits in the SECOND column; every label sits in the third. That means (a) a section's rows start after its chevron, at `calc(--pv-sec-glyph + --pv-sec-gap)` on `.pv-side-section-rows`, never at the chevron itself, or a bookmark sits further left than every row of the tree below it; (b) a row's icon-to-text gap is its heading's gap (`--pv-sec-gap`), or the labels miss each other by the difference — three pixels, and visibly ragged; (c) a row's icon BOX is `ICON.ui` wide like the heading's glyph, or the text lands a pixel off even with the gap matched. All three are the header's own geometry, named once, so a change of icon size or gap carries; the E2E asserts the ALIGNMENTS, not the pixels. The whole padding lives in the class: an inline `padding` shorthand beats a stylesheet `padding-left`, which is how the indent silently did nothing on the first attempt.
- **Comment column** — a comment sits BESIDE the place it talks about (encryption package, Stufe D/D2; `.pv-comment-column`, `.pv-comment-card`). The column is a sibling of the note body inside one flex row — not an overlay, and not the collapsed list ABOVE the text it replaced. Each keeps its own scrolling, and the note keeps its readable measure. It exists only where the vault can carry comments at all; elsewhere the wrapper is `display: contents`, so a plain vault renders exactly the layout it did before.
  **The card and its range in the text are ONE thing seen twice.** The active card wears the `--accent-container` pair, the same comment's range in the editor wears the same tint, and selecting either selects the pair. There is no third emphasis — and a comment whose anchor no longer resolves tints NOTHING and says so on the card, because a tint on a guessed position is worse than none.
  A **quote** on the card is the anchor's own stored text in a bordered well, never a re-slice of the current document: the text may have changed since, and the card must show what was commented on. The author line carries the display NAME from the workspace policy with the member id as its tooltip — a name is a claim the policy carries, not a verified identity, so the technical id stays reachable.
  A **mention** (`@Name`, `.pv-comment-card__mention`) is a tinted run inside the body, not a chip: the body is Markdown a stranger's editor also shows, so the highlight may not change a character of the text. It is derived on every render from the member list rather than stored — one truth, and a renamed member changes what the card shows with nothing to migrate. A thread that names YOU sorts to the top of the column and carries a `.pv-comment-card__state` badge saying so; a resolved one deliberately does neither, because it needs no attention any more and floating it would push the open threads down for nothing.
  Replies belong to their thread and never carry an anchor of their own. The compose box for a NEW comment sits at the bottom of the column behind a hairline (`--new`) and names its target in a sentence, because what the comment will attach to is the selection — which the user can no longer see once the focus moved into the text field.
  **A property is commented on where it is edited** (Stufe E, E2; `.pv-comment-dot`). A frontmatter property has no range in the body, so it cannot be selected — the affordance has to sit on the row that shows it. It is a small dot, not a full IconButton: a properties row already carries a type button, a value control and a delete button, and a fourth control of that weight would turn the densest row in the panel into a toolbar. The dot appears on hover like the row's other secondary controls, and STAYS visible when the property already carries comments, with the thread count beside it — an existing conversation is information about the note, not a control that may hide. It counts THREADS, never messages: a reply inherits its thread's anchor and carries none of its own, so counting messages would inflate one busy discussion into the appearance of many separate remarks.
  **The column is a head, a scrolling body and a docked foot** (correction round 2026-09-03, K3). The head names the surface with the count of OPEN threads beside it, offers the filter `Open · All` (a `Segmented`), the mute bell and a close button; the body scrolls; the compose box sits in the foot behind a hairline, so it stays reachable however long the list is. A card opens with ONE line that says who and when: an initials chip (`.pv-comment-card__avatar`, hue derived from the member id - the same person keeps the same colour everywhere, nothing stored), the display name, and a relative time (`relativeTimeLabel`, spoken by `Intl.RelativeTimeFormat` in the app language, the full timestamp as its tooltip). The action row is `--quiet` on a pointer that can hover: it appears on hover, on the selected card and on focus-within; where nothing hovers (`@media (hover: none)`) it is always there. The column is a choice, not a fixture: a toolbar `IconButton` with the open count (`.pv-comment-toggle`) shows or hides it, remembered per vault; a note without that memory opens the column only when it carries open threads. A click on a tinted passage, a comment request from a widget and a jump from a notification bring it back - the compose box lives in it. The phone's sheet uses the same head, chip and cards; only the toggle (the sheet itself) and the always-visible actions differ, both recorded in the parity catalog.
  The dot's target is a KEY, not a passage, and the two must not share a route: a property comment writes no marker into the Markdown at all (the key is the anchor), while a text comment wraps its range in a marker pair. Folding them into one path would put an HTML comment inside the YAML frontmatter — valid nowhere, and corrupting exactly the block the anchor depends on.
- Pane heads: title left, actions right as IconButtons.
- Empty surfaces render EmptyState, not bespoke prose divs. An empty state **explains and offers exactly one action** (mobile rework N7): it names why the surface is empty and, where the surface can be filled, carries a single tonal Button to fill it. Three shapes are exempt and only three: a SUCCESS ("no orphans found" — nothing to do IS the answer), a state whose filling is a gesture somewhere else entirely (a bookmark is set ON a note, a tag is written IN one — a button there would promise what it cannot do; the sentence names the gesture instead), and a passive log that fills itself. What an empty state must never do is claim a shipped feature does not exist: when only the index is missing, it says so and offers a retry. On the phone the state sits on the container grammar's card surface rather than loose on the page background — an empty surface is the surface's content, not a grey sentence dropped onto it.
- Connect wizards: numbered steps left to right (provider → services → sign-in); the service selection drives which permissions are requested; every service gets a status line covering success, waiting and error; the account-destroying action is always last and danger-styled.
- Cascade deletes: the always-deleted target sits first (no checkbox); every consequence group is its own card with a group checkbox and a count pill; anything from linked databases and every shared/multi-membership element defaults OFF (badge explains why); the danger button always counts the actual selection.

Task planner and quick capture (tasks view, 2026-09-20): the tasks view shows ONE of five lists — Today (with Overdue on top), Upcoming (by day), Inbox, All, Done — defined once in `TaskPlannerNav` and drawn as a **rail** beside the list on the desktop (`.pv-planner-rail`, rows from the container grammar; the active entry uses the accent-container pair via `.is-on`; a second group lists the most frequent tags as one-click tag filters) and as a **segment** above the list on the phone (`Segmented`, scrolls sideways when five labels do not fit). The planner lists are `TaskPlannerList`: `SectionLabel` + `GroupCard` + `Row` per section, a row being state box (open, in progress, done, cancelled — four glyphs, never colour alone), optional priority flag (`.pv-planner-flag`, warning tone for high, accent for medium, muted for low — never the error red, which means danger), title, and a wrapping meta line of chips (time or day, repetition, tags) that ends in the row's source. "All" is the view as it has always been; the open/done/all status filter belongs to it alone, because a planner list answers that question itself. Quick capture (`TaskCaptureField`, `.pv-capture*`): ONE text field whose text is the model. Recognised words are marked INSIDE the field — a mirror layer (`.pv-capture-mirror`) behind a transparent `TextInput`, same box, font and inset, following the input's scroll position — and listed below it as removable chips ("bricks"); a brick switched off stays visible as a muted chip and its words count as title again. Nothing is applied that was not shown first. The phone hosts the same field in a sheet with a row of quick chips (`.pv-capture-quick`) that WRITE into the sentence rather than keeping a second state. Docking: the rail, rows, chips and cards are primitives both easter-egg themes already restyle; `.pv-capture` carries its own LCARS and Win95 rules because the field's ground moves to the mirror layer (an opaque themed input would hide the marks).

Journal (stream, capture, day section; 2026-09-20): a journal entry is a list line of the daily note, and every surface draws it as that line — the **time as a column** down the day (`.pv-journal-time`, `tabular-nums`, shown in the clock of the app's language), the state box of a task entry in front of its text (the four glyphs of the planner, never colour alone), then the text through the shared inline renderer (links open, tags are the editor's pills, an image embed is a preview instead of its syntax). Everything hangs on the FIRST line: the row aligns to its top, and the box and the "more" button are centred on a box of one line's height (`--pv-journal-lh`) — so a six-line entry does not push its controls to the middle. Interface round (2026-09-22) — five patterns that came out of one free test round:

- **Key/word pairs** (`ShortcutHints`, `.pv-shortcut-hint`). A line of keyboard help is never one sentence: each shortcut is its own unbreakable box (`white-space: nowrap`), and the line wraps BETWEEN pairs. Written as prose it broke in the middle of "Shift+Enter starts a new / line", and in a different place in each of the ten languages. Key caps stay untranslated, the way `acceleratorLabels` already prints the global shortcut: they name what is written on the keyboard, not a word.
- **One search field, one place** (`BaseSearchField`, `.pv-basesearch`, `.pv-basesearch-row`). A database's search renders the app's `SearchField` — same height, same magnifier, same ✕, same Escape contract — and its POSITION never depends on the surface it serves: the magnifier sits with the head's actions and opens a row underneath, whether the database has two views or eight. Closing that row clears the query, because a filter nobody can see is how a list comes to look broken. A surface with no head of its own (an embedded board) is the one place a field lives in the content. The desktop row (plan Befunde 2026-09-24, E18) sits on `--bg-secondary` with a `--border-color` line; the FIELD grows with it — at least 16 rem, at most 40 rem, never the 20 characters a browser gives an input without a width of its own — and the hit counter stands at the row's END, not glued to the field. The Escape contract reaches through `BaseSearchField` (`onEscapeWhenEmpty`): the first Escape clears, the second closes the row and hands the focus back to the magnifier. The phone's row already takes its line and stays as it is.
- **Shrink, then overflow — never a scrollbar** (`tabWindowOf`, `.tabstrip-more`). A strip of repeated items shrinks its items to a floor where they are still themselves (icon, cut title, close), and what does not fit then goes behind ONE button with a count, one click away. A horizontal scrollbar inside chrome is not an answer: nobody looks for one there, and it turns a click into a drag. The active item is always inside the window.
- **A dense row for a narrow column** (`.pv-journal-slim-row`). A side column of 250px is not a list page: the content row's 52px metric was built for a settings line, and three short entries filled more than 150px of it. A dense row is one line, starts on the same text edge as every other row, and carries no control — a 13px box in a 250px column is a misclick waiting to happen. State is a quiet MARK on the trailing edge; acting on the row happens where the target is finger-sized.
- **A new entry is written in the real editor** (plan Befunde 2026-09-24, E14–E17; `PinboardEntryModal`, `.pv-pinentry`; phone: `PinboardEntryScreen`, `.m-pinentry-*`). Where a surface lets a person write a note from scratch, it offers the editor every note has — live view, completion, pasted images, the slash menu — never a text area that shows Markdown as raw characters until it is saved. The desktop hosts it in a large `Modal`: a title field that reads as the heading (a frameless `TextInput`, its focus a line under it), the editor, a line of inherited values as removable chips, and a footer of key/word pairs (`Ctrl/⌘ Enter` save, `Esc` close) before a ghost **Discard** and a primary **Save**; the destination folder is the header note. The phone uses a PAGE of its own, not a sheet — the keyboard and the docked formatting bar need the room — with the same title field (`.pv-pinentry-title`, the phone's inset on top), the chips above the text (below it they would sit under the docked bar), the editor, and in the app bar the back arrow every pushed page has, **Discard** as an icon and **Done**. The file exists from the first moment (an editor needs one: images land beside the note), so the surface only ENDS the entry: Save keeps it, closing (X, Escape, back) keeps whatever was typed and silently takes back a draft nobody wrote into, and only Discard removes content, after a question. An empty board's empty state offers the same entry on both shells. Escape is the window's unless something inside the editor is on screen to take it: a completion that is only running after a keystroke (`closeVisibleCompletion`) does not swallow it. All parts are existing primitives; `.pv-pinentry` is layout only and needs no LCARS or Win95 rules of its own.
- **One sign per meaning in a calendar** (`.pv-datejump-day.has-mark`, the sidebar calendar's day cell). Dots under a day belong to APPOINTMENTS. A day that carries a daily note is therefore marked on the NUMBER — set in bold with a quiet ring — not with a second dot and not with a sun in one calendar and a dot in the other. Two signs for one thing, or one sign for two things, are the same bug seen from either side.
- **A card of choices: one form, three cases** (`ChoiceMark`, `SortSheet`, `MobileDialogHost`; E11 of the same round — promised there and written down only with the correction of 2026-09-24). A choice is ONE component in a card of rows, and its form says what a tap will do. (a) **Single choice** — a round mark, exactly one filled; the tap moves the mark and the sheet closes after a visible beat (`CHOICE_BEAT_MS`, 300 ms), so nobody wonders whether the right one was hit. (b) **Multiple choice** — a SQUARE mark with a check inside; the sheet holds until **Done**. (c) **Sort** — a single choice plus a direction: round mark on the left, the direction as an arrow on the right, a second tap on the active key reverses it — a line under the card says so — and the sheet holds until **Done**, because the direction is decided while looking at it. Every ordered list on the phone opens this one sheet (`SortSheet`: folder view, search hits, backlinks — the backlinks had chips of their own), under the sheet's own title like every other sheet. Round is one, square is several — the distinction Plainva already makes between an option and a checkbox. The class `.m-slotmark` is written ONLY by `ChoiceMark` (`choiceSurfaces.test.tsx`).

Lists on the phone (correction of 2026-09-24, E20) — **only a choice wears a mark.** The 22.09. round filed the areas sheet as a card of choices, and the build gave it rings; its mockup had it right. A row list is one of three kinds, and the kind decides the form:

- **Choice** — a VALUE with a state (language, sort, the calendar of an event). Ring or box as above; the ring sits on the value in force (`mSelect` with `value`, `mMultiSelect`). A choice without a current value is a list of empty rings that reads as an unanswered setting, so every `mSelect` without `value` carries a written reason in the guard (today only the bulk edit, where the selected rows may disagree).
- **Target** — a PLACE one goes to, or the target of an action: the areas, the views of a database (strip overflow and configure sheet), the vaults, "Move to" in mail, the database a task is promoted into. No mark at all. The place shown now is `Row`'s `current`: the accent-container pair, weight 600, a check on the trailing edge and `aria-current="page"` — the same idiom as every selected row in the app. "Shown now" means on screen: an area outside the bar opens on top of a tab, and the areas sheet then marks that area, not the tab below it (`currentArea`). Where the object already lies (a mail's own folder) stays in the list with the word **here** and cannot be chosen, so the list reads complete. A target closes on the tap (`mTargets`, `current`, `here`).
- **Action** — something one DOES: "Insert" (camera, gallery, file), "Open image", this occurrence or the whole series, the first step of a flow that forks. Plain rows, nothing preselected, nothing tinted; the recommended entry stands first, a destructive one is separated as in every sheet (`mActions`). "Insert" had the camera preselected, which claimed a state no action has.
- **The fork of a flow is an action** (the borderline case): "a vault on this device / online / an existing folder", "an existing vault / a new one", the structure template of a new vault. Nothing is in force before the answer, each row starts a different way, and the desktop's start screen shows the same answers as cards to click — so the phone shows plain rows too. A question whose answer becomes a property of something that already exists (the export format of this note, which defaults to the list) stays a choice.
- A sheet of places that has two runs of rows separates them with a named divider (`.m-sheet-divider`: the section label's micro caps with the hairline carried to the edge), under the sheet's own title (`.m-sheet-title`). The areas sheet used to open with a heading "Areas" and continue with "Not in the bar — reachable via Areas", written inside Areas.

The desktop needed none of this: navigation there is `MenuItem active` and choices are native checkboxes and radios.

Related notes (AI harness P2b-4, 2026-10-01; `RelatedNotesList`, `RelatedNotesMenu`, `RelatedNotesActions`, `.pv-related-*`): at most three notes close in meaning to the open note and not linked with it yet, computed on this device from the vectors search by meaning already keeps — never a request. On the desktop it is the section **Related** of the right sidebar, after Backlinks (backlinks list what is linked, this what is close and not yet linked); like every section it disappears when it has nothing to show (plan E6), and it has a count in its head. On the phone it is the tab **Related** of the note sheet, after Backlinks, present while the AI is on; the tab says in one quiet line why it is empty ("Nothing close enough.", still reading this note, paused, search by meaning off). A row is the note's title in bold with a file icon, opening the note on a click, and under it one `--text-muted` line naming the pair of sections — "Production ↔ Shooting days › Split" — followed by "both mention [[…]]" when both notes link to the same note. An `IconButton` of size `sm` with the info icon at the row's end opens **Why this hint?** under the row (`.pv-related-why`, a thin rule on the start side): the two sections with their heading chains and their first words, each a text button that jumps to that section; "very close in meaning · not linked yet · computed on this device" in `--text-muted`; and two ghost buttons, Open and **Not helpful**. "Not helpful" hides exactly that pair of notes on this device — never what search finds, never another pair. A note is paused from the section's menu (the head's `MoreHorizontal` `IconButton`: "Pause for this note", "Pause in this vault"); on the phone the same two as ghost buttons under the tab's list. A paused note keeps its section with one line and a ghost "Show again for this note", because that is where the pause is lifted; a paused vault shows no section at all and is lifted in the settings. The settings add one `Switch` row "Show related notes" to the card of search by meaning (App world), and plain rows for what the reader said: "Paused in this vault" with Resume, the paused notes with "Show again", the hidden hints with "Bring back". No theme selectors of their own: the rows are text runs in tokens and existing primitives; `.pv-related-*` is layout only.

## Theming duties (docking matrix)

### Account setup, file comparison and compact navigation

Account details render every supported service with an explicit action: open its settings, add it, or sign in again. Setup is a focused sequence: connection, resource selection, result. The selected account and destination vault remain visible. General calendar/reminder settings follow setup. Mobile hides the main navigation during the focused flow; Back and End setup remain available inside it. Error messages offer the next useful action without exposing credential implementation details.

Conflict comparisons identify both files using wrapping vault-relative paths. The compact file context stays above the scrolling diff. Each side offers Copy path and Show in folder. Task comparisons show their human fields first; proven different identities offer Keep as separate tasks. Replacement explicitly names the direction and subsequent removal of the conflict copy, including both paths in confirmation. Desktop retains its editable merge surface. These arrangements use existing card, banner, button and sheet primitives and inherit their LCARS/Win95 docking.

A rename proposal (the clean-up of task-note names, plan Befunde 2026-09-24, E12) is a banner that says what and why — including how many links follow, all together — with its two actions, above ONE card of rows. Each row reads "old → new": the old file name as a `<del>`, struck through in `--text-muted`; a `meta` arrow in `--text-faint`; the new file name in `--text-main`. Never a colour of its own, and names wrap rather than being cut, because showing both names is the row's whole job. Banner, card and row carry the theme; `.pv-names-notice` only stacks them and lays out the row, so LCARS and Win95 need no docking of their own. The action that renames is `primary` and always confirms first; the one that puts the proposal away is `ghost`.

The mobile navigation capsule keeps `--space-2` of vertical padding even when labels disappear. Touch targets remain at least `--touch-md`; the selected pill uses `--space-8` height. Safe-area padding is external to the capsule, and content/FAB offsets include its full height. The tablet/desktop rail retains the same positive inset principle.

Every top-level `pv-*` surface defined in ui.css must either carry LCARS **and** Win95 selectors or a justified entry in `designGuards.test.ts`'s `THEME_EXEMPT` map. The shared chip slots (`--chip-0..7`), graph knobs (`--graph-glow-intensity`, `--graph-edge-curvature`), `--edge-scrim` and the callout palette are part of a theme's contract — details and prohibitions in `Theme_Platform.md`.

The current row of a target list (`.pv-grouprow--current`, E20) is a state of the shared row, not a surface: it paints from the `--accent-container`/`--on-accent-container` pair, so every theme that sets the pair docks it — under Win95 the container is the full navy, which is why its icon and second line inherit the pair instead of keeping their greys.

Mobile `m-*` surfaces carry a different duty, because their failure mode is a different one. Twelve of the fourteen themes are pure token overrides and name no selector at all; what put mobile out of their reach was never a missing docking rule but a **literal** — one hard colour or shadow recipe takes a surface out of every theme at once, and no theme file can win it back. So the rule for a mobile surface is: **paint through the shared tokens.** Docking into LCARS/Win95 on top stays a design decision, taken where their shape language (bevels, Okuda bars) genuinely differs from the default — as `.pv-card` and `.pv-sheet` do.

## Paired personal theme

My design edits light and dark moods through the existing preview, colour controls, segmented selector and settings cards. Each mood keeps its colours; radius is shared. An absent counterpart is a labelled proposal, retained only after the primary Adopt action. Editing a proposal never changes the saved design. While the page is open the whole app wears the mood being edited, a proposal included (plan Befunde 2026-09-24, E22), and an info `Banner` with the eye glyph (`CustomThemePreviewBanner`, the Banner's `icon` slot) says so and names what applies after leaving; leaving restores the stored Mode/System without saving anything. A theme that pins the mode shows the pinned value in a disabled mode control on both shells (desktop `Select`, phone `Segmented` with `disabled`) and says why underneath. Once both moods exist, the normal Light/Dark/System preference selects between them. The personal sync switch is opt-in on each device; turning it off keeps the local design. Concurrent variants are shown with both mood swatches and a named Use this variant action. They remain available until that explicit choice resolves the conflict. Existing Banner, Button, Switch and card docking applies; no new surface family or raw colour tokens.

## Note text in either direction

Note text may be written right to left (Arabic, Hebrew, Persian and the other RTL scripts; issue 111). The interface is **not** mirrored and keeps its language; only the note's text turns. One rule decides: a block (paragraph, heading, list item, the paragraphs of a quote or callout, a table and each of its cells) runs the way its first strong character behind the Markdown syntax says, read from the source by `textDirectionOf` / `lineDirections` (`packages/ui/src/lib/textDirection.ts`). The editor sets the result as an explicit `dir` on each line (`textDirectionExtension`, with `EditorView.perLineTextDirection`), the desktop reader on each block (`rehypeReaderDirection`), so the two never decide differently; fenced code, math blocks and the frontmatter stay left to right. Cards use `dir="auto"` per text block (rendered text, no syntax left); names in interface rows (file tree, search results, `Row`) are wrapped in `<bdi>` so they order their own characters without moving in the row.

Everything that lays out note text sets its sides **logically** — `padding-inline-start`, `margin-inline-end`, `border-inline-start`, `text-align: start` — which is identical to the physical side for a left-to-right line. `designLint.test.ts` counts the logical spacing names in `rawSpacing` and fails a physical left/right spacing, border or alignment in the note-text files (editor theme, list indent, live-preview tables, reader, cards).

## Enforcement: the three test nets

Task checkbox rows keep their note path as context and display recognized Tasks metadata on a wrapping, muted text line. Created, start, scheduled and completed dates are named; the ID remains explicit. The original recurrence text is visible. An unsupported recurrence adds a short warning that the rule is preserved without automatic continuation. This metadata adds no panel or new control; it follows the existing task row and token colours in both shells.

The mobile share inbox follows the existing sheet contract: content preview, wrapping file names, named vault/folder destination, inline error, ghost Later/Cancel and primary Import. A pending transfer is an inline Banner above the app header; it owns the top safe-area inset while present. Discard is a separate ghost action with the existing danger confirmation. These use the established Banner, Button and sheet docking, without another colour or surface family.

- `designLint.test.ts` — value ratchet. Budget map file → rule → count; fails on any EXCESS and on stale entries. After the 2026-07-19 sweep the map holds only documented data/native-attribute/iframe/local-stacking exceptions; any raw value in ANY other file (including new ones) fails immediately. New entries require a review-visible justification comment; the map only ever shrinks.
- `designGuards.test.ts` — structure, across BOTH shells' stylesheets: classExistence (referenced `pv-`/`m-`/`base-cfg-` classes must be defined), cssDuplicate (no selector defined twice within one bundle), themeCoverage (the docking matrix above), duplicateDeclaration (a property is set at most once per block), declaredVariables (no bare `var()` on a custom property nothing declares — a `var(--x, fallback)` degrades on purpose and is fine), touchTargets (nothing interactive in the mobile shell under `--touch-sm` = 44px) and themeReach (mobile surfaces paint from tokens, never literals).
- `mobileLint.test.ts` — the mobile twin, running the **same rule set as the desktop** since 2026-08-02. Mobile used to be watched by seven of the fifteen rules; a ratchet that watches one shell is half a ratchet.

## The process rule (new visual patterns)

**Catalog first, build second.** A new visual pattern (a new surface, control shape or arrangement) starts by extending this document, `design-styleguide.html` and — where applicable — the docking matrix, and only then gets built on tokens + primitives.
