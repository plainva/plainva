# AI harness threat model

Scope: the AI harness in both shells, Plainva's MCP server and client, skills and scripts (ADR 0017–0022). It complements the [encrypted workspace threat model](Encrypted_Workspace_Threat_Model.md). Every control named here has a test or an eval in CI, or a package that builds it; nothing is "later" without a trigger.

## What is protected

- **Vault content**, above all what the policy keeps local (`plainva.ai: {cloud: deny}`, folder rules, encrypted workspaces) and the sensitive classes (mood, place stamps).
- **Provider keys and account tokens** (keychain, `SecureStore`).
- **The user's approval** — the one grammar of proposals, and the scope approval of the send overview.
- **Third parties** — mail recipients, event attendees, members of shared workspaces.
- **Device integrity** — nothing the harness does may run code outside the declared tools.

## Who attacks, and from where

| Entry | Example |
|---|---|
| Prompt injection in tier 3 content | a note synced from another device or imported from a web clipper, a mail, an event description, a web page, an MCP tool result, script output |
| Content that arrives as instructions | a skill, memory rule, routine or vault-root `AGENTS.md` that appears through sync, import or a shared folder |
| Local processes | anything running as the user, reaching for the MCP channel |
| The WebView | script that runs through a rendering bug in untrusted content |
| Providers and gateways | a recipient that stores more than promised, a gateway the user did not choose |
| The model itself | a wrong tool call, a wrong edit, an invented source |

Hidden roots never. ## Reviews made for P0

- **CSP.** The desktop CSP allows `img-src 'self' blob: https: data:` and `connect-src 'self' https: ipc:`; the HTTP plugin allows `https://**` and `http://**`. Remote images in notes are a feature and stay. AI-written content goes through the pre-write linter before it is stored (T1), and AI calls do not use the WebView's network at all — they run through the native egress with its own allowlist. A per-vault switch "load remote images in notes" (like mail's `allowRemoteImages`) would narrow T1 further for content the user wrote; it is a candidate, not part of the harness.
- **CORS.** Irrelevant for the harness: provider calls run in Rust, Kotlin and Swift, not through the browser's `fetch`. For the record: Anthropic allows browser calls with an explicit opt-in header, OpenAI and Gemini do not.
- **Telemetry.** No provider SDK, so no SDK telemetry to audit; the adapters send nothing but the request (conformance suite).

## Residual risks

- A script running in the WebView (a rendering bug) can use the session — ask the harness things, read what the WebView can read — but it cannot read keys, widen the egress allowlist or bypass the approval of proposals, which the native side and the user carry.
- Renderer extensions (diagrams, math) that fetch or link on their own are reviewed with the proposal surfaces (P1.5): the linter covers Markdown and HTML destinations, not a diagram language's own link syntax.
- A person can approve a harmful proposal. The proposal shows the full diff, the author, and what the linter defused; it does not decide for them.
- Malware running as the user can read the vault files directly; no harness design changes that.
- A person can approve a request whose address carries data. The question shows the whole address and says when the model composed it itself; it does not decide for them. A site allowed for good sees every named address that is fetched from it, and — like any site a browser visits — the device's IP address.
- On iOS the page fetch cannot bind a connection to the addresses it checked (URLSession offers no such handle). It checks every address of the name before the request and the far end the system reports after it, before anything of the answer is used: a name server that answers twice differently can make one GET without a body reach a private address, never its answer a model. The desktop and Android connect to exactly the addresses they checked.
- A search goes to the provider of the model, which sees the query and hands it to its search service; the reader in quarantine is a second call to the same provider. Neither sees more of the vault than the conversation already sent.
- Without a model on the device, a message's text goes to the conversation's provider to be read — after the user allowed mail for that provider. The question says so before, and the run's record says who read. A report can repeat what a message says, so what a stranger wrote can still reach the answer as a statement about the message; it cannot arrive as an instruction, a tool call or a live address.
- A sender or a subject is a stranger's words and reaches the model that holds the tools, capped and fenced like the title of a page a search returns. It can lie; it cannot carry an address the user could follow or that a request would fetch without asking.
- An approval of mail holds for a recipient until the app closes. Within it, a run can search and read any message of the connected accounts; a request to the internet in such a run still asks each time.
- Searching mail asks the user's own mail server, with the user's credentials, through the mail client the app already uses; the first successful fetch of an account is noted once in the settings, as it is when the user opens the mailbox.
- A model that reads a picture reads all of it: a face, a screen in the background, a line of handwriting at the edge. The overview shows the picture exactly as it goes; it does not look into it for the user — the hint "possibly sensitive" reads text, not pixels.
- Which notes embed a picture is found by the file's name in the notes' text. Two pictures of one name in different folders count as one, which can only keep a picture back. An embed whose name is written in a way the scan does not look for — a non-ASCII letter in another case, a partly encoded name — is not found, and neither is an embed in a note the index has not read yet; the picture's own folder rule, and the door inside the note, do not depend on the scan.
- The copy of a picture that was sent stays in the conversation's record in the app's data, on this device, until the conversation is deleted or its retention ends. It is the record of what a provider got; it is also a second copy of the picture.
- A picture is read by the model that holds the conversation's read tools, as a note is. Text in it can therefore make the model look things up in the vault and say untrue things; it cannot make a request leave, change a note or move the app — the door's conversation has no such tool, and any other run asks for each outside effect.
