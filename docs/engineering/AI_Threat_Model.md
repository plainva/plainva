# AI harness threat model

Scope: the AI harness in both shells, Plainva's MCP server and client, external agents, the system's assistant on the phone, skills and scripts (ADR 0017–0026). It complements the [encrypted workspace threat model](Encrypted_Workspace_Threat_Model.md). Every control named here has a test or an eval in CI, or a package that builds it; nothing is "later" without a trigger.

## What is protected

- **Vault content**, above all what the policy keeps local (`plainva.ai: {cloud: deny}`, folder rules, encrypted workspaces) and the sensitive classes (mood, place stamps).
- **Provider keys and account tokens** (keychain, `SecureStore`).
- **The user's approval** — the one grammar of proposals, and the scope approval of the send overview.
- **Third parties** — mail recipients, event attendees, members of shared workspaces.
- **Device integrity** — nothing the harness does may run code outside the declared tools.

## Who attacks, and from where

| Entry | Example |
|---|---|
| Prompt injection in tier 3 content | a note synced from another device or imported from a web clipper, a mail, an event description, a web page, an MCP tool result, script output |
| Content that arrives as instructions | a skill, memory rule, routine or vault-root `AGENTS.md` that appears through sync, import or a shared folder |
| Local processes | anything running as the user, reaching for the MCP channel |
| The WebView | script that runs through a rendering bug in untrusted content |
| Providers and gateways | a recipient that stores more than promised, a gateway the user did not choose |
| The model itself | a wrong tool call, a wrong edit, an invented source |
| An external agent | a program of another maker that the user started in the vault's folder: what it reads and sends on its own, what it asks the host for, and what it says and names in its session |
| The system's assistant | Siri, Shortcuts and the assistant behind them on a phone: what they do with a title Plainva let them read, and what somebody — a voice near the phone, a shortcut from elsewhere — makes them ask Plainva to write |

## Reviews made for P0

- **CSP.** The desktop CSP allows `img-src 'self' blob: https: data:` and `connect-src 'self' https: ipc:`; the HTTP plugin allows `https://**` and `http://**`. Remote images in notes are a feature and stay. AI-written content goes through the pre-write linter before it is stored (T1), and AI calls do not use the WebView's network at all — they run through the native egress with its own allowlist. A per-vault switch "load remote images in notes" (like mail's `allowRemoteImages`) would narrow T1 further for content the user wrote; it is a candidate, not part of the harness.
- **CORS.** Irrelevant for the harness: provider calls run in Rust, Kotlin and Swift, not through the browser's `fetch`. For the record: Anthropic allows browser calls with an explicit opt-in header, OpenAI and Gemini do not.
- **Telemetry.** No provider SDK, so no SDK telemetry to audit; the adapters send nothing but the request (conformance suite).

## Residual risks

- A script running in the WebView (a rendering bug) can use the session — ask the harness things, read what the WebView can read — but it cannot read keys, widen the egress allowlist or bypass the approval of proposals, which the native side and the user carry.
- Renderer extensions (diagrams, math) that fetch or link on their own are reviewed with the proposal surfaces (P1.5): the linter covers Markdown and HTML destinations, not a diagram language's own link syntax.
- A person can approve a harmful proposal. The proposal shows the full diff, the author, and what the linter defused; it does not decide for them.
- Malware running as the user can read the vault files directly; no harness design changes that.
- A person can approve a request whose address carries data. The question shows the whole address and says when the model composed it itself; it does not decide for them. A site allowed for good sees every named address that is fetched from it, and — like any site a browser visits — the device's IP address.
- On iOS the page fetch cannot bind a connection to the addresses it checked (URLSession offers no such handle). It checks every address of the name before the request and the far end the system reports after it, before anything of the answer is used: a name server that answers twice differently can make one GET without a body reach a private address, never its answer a model. The desktop and Android connect to exactly the addresses they checked.
- A search goes to the provider of the model, which sees the query and hands it to its search service; the reader in quarantine is a second call to the same provider. Neither sees more of the vault than the conversation already sent.
- Without a model on the device, a message's text goes to the conversation's provider to be read — after the user allowed mail for that provider. The question says so before, and the run's record says who read. A report can repeat what a message says, so what a stranger wrote can still reach the answer as a statement about the message; it cannot arrive as an instruction, a tool call or a live address.
- A sender or a subject is a stranger's words and reaches the model that holds the tools, capped and fenced like the title of a page a search returns. It can lie; it cannot carry an address the user could follow or that a request would fetch without asking.
- An approval of mail holds for a recipient until the app closes. Within it, a run can search and read any message of the connected accounts; a request to the internet in such a run still asks each time.
- Searching mail asks the user's own mail server, with the user's credentials, through the mail client the app already uses; the first successful fetch of an account is noted once in the settings, as it is when the user opens the mailbox.
- A model that reads a picture reads all of it: a face, a screen in the background, a line of handwriting at the edge. The overview shows the picture exactly as it goes; it does not look into it for the user — the hint "possibly sensitive" reads text, not pixels.
- Which notes embed a picture is found by the file's name in the notes' text. Two pictures of one name in different folders count as one, which can only keep a picture back. An embed whose name is written in a way the scan does not look for — a non-ASCII letter in another case, a partly encoded name — is not found, and neither is an embed in a note the index has not read yet; the picture's own folder rule, and the door inside the note, do not depend on the scan.
- The copy of a picture that was sent stays in the conversation's record in the app's data, on this device, until the conversation is deleted or its retention ends. It is the record of what a provider got; it is also a second copy of the picture.
- A picture is read by the model that holds the conversation's read tools, as a note is. Text in it can therefore make the model look things up in the vault and say untrue things; it cannot make a request leave, change a note or move the app — the door's conversation has no such tool, and any other run asks for each outside effect.
- An answer kept as a note can be wrong, and the note then says something wrong in the user's vault. The note names who wrote it and what the run really read; it does not check the answer against its sources. A source in the list was read by the run — whether the answer follows from it is the reader's to judge.
- A statement an injected page planted in an answer is kept with the answer. It arrives in the note as text: no address in it can be followed, nothing loads, and the page it came from stands in the list of sources.
- The list of sources names the pages a run read, with their whole addresses. A note kept in a shared workspace, or published, shows those addresses to its readers; the question before such a note says who reads it, it does not show the list.
- A skill that names the internet's tools reaches for them in every conversation the user starts with it, in a vault that allows the internet. The user chose that by starting the skill, not by pressing the globe; the overview before the first request and the conversation's first line say that it may use the internet, and each request asks while notes are in it.
- A reader's report can repeat a hostile sentence as a fact with its quote, inside the fence. What reaches the model with the tools of a stranger's text is therefore not "nothing", it is "nothing that is not marked as data" — and nothing that the reader did not write down as a report.
- A kept note inherits the rules of what the conversation carried and what its tools let through. It does not know what the user typed or pasted into the conversation: text copied by hand from a note kept from the cloud arrives in the kept note without that note's rule. The rules are those in force when the note is made — a rule added to a source afterwards does not reach notes kept before — and a rule the kept note carries stays until the user removes it, also when the source's rule is lifted.
- Inheriting is deliberately coarse: one restricted note anywhere in the conversation up to the answer restricts the note made of it, whether or not the answer used that note. The toast says that the note carries the rules of what it rests on; the properties show which.
- Other AI-written text stays under the rule of the note it belongs to — a suggestion, a transcript, a reply in a comment thread. Text the user takes over by hand from an answer (copy, paste) is the user's own step, as it is with any other text.
- A person can approve a foreign server whose descriptions are an attack, and say yes to a call whose arguments carry what they did not mean to send. The review shows the texts as the server's words, the question shows the arguments in full; neither decides for them. Allowing a folder for a server is allowing its content to go there: once a conversation has read a note in it, what a model writes of that note into arguments is checked by the person's look alone.
- No folder rule covers what a conversation read that is not a note: the user's mail and appointments (as a report of the reader in quarantine), a page, another server's result. A model can write any of it into the arguments of a call to a foreign server; the question shows them, and nothing else stands in the way.
- A pin covers what a server says, not what it does. A tool that claims to only read can do anything on its own side with what it is sent; within the five minutes a server's freshness hint may count, a changed listing is not noticed — a model reads the snapshot in that time, and every call is still asked.
- A program a user registers as a server is code they chose to run. Where the sandbox does not hold — on Windows there is none — it runs with their rights; the system's dialog shows the whole command line, and a command that starts a shell is pointed out, not forbidden.
- The MCP client has met no server but the scripted one of this repository; the Swift side and the sandbox on macOS and Linux have not run on a device ([review](MCP_Client_Security_Review.md), "Not verified").
- An external agent is a program with the user's rights, and no rule of the vault reaches what it does on its own: it can read a note kept from the cloud, send it, and change or delete files without a suggestion. Plainva says this before every start and for as long as a session runs; it prevents none of it. A change an agent makes itself and does not report is not seen at all.
- Registering an agent raises what a script in the web view (a rendering bug) could reach. The protocol is spoken in the web view, so such a script can speak to an agent that runs — hand it a prompt, answer its questions, name it programs to start as its tools — and an agent runs commands: that is code execution with the user's rights through the agent. Before it stand the two dialogs of the system (registering an agent; the first start of an agent in a folder since the app started), which the web view cannot answer. After a yes to a start, nothing native stands between the web view and that agent in that folder until the app is closed.
- The words of the two dialogs come from the web view; the folder and the command below them are written natively. A script in the web view could word the question to mislead, not change what it is about.
- A sign-in in a terminal runs the registered program with arguments and values the agent named, in a window the user sees. The names of the values are restricted and every part is quoted; what a program does with an argument it was given is the program's.
- The trust in an agent is the user's: Plainva checks no agent, pins no version of one and does not know what an update changed. An agent that was honest when it was registered is the same command line after it changed.
- What an agent asks the host to write becomes a suggestion a person can accept. A round shows every change, the agent's name and what the linter made inert; it does not judge the change. Accepting a harmful round is the person's step, as with any proposal.
- A note an agent wrote and the user created carries who wrote it — the agent's id on this device. That is the user's name for a command line, not a verified identity of a program or of the model behind it.
- An agent hears why Plainva refused a file, in one fixed sentence: that a note is kept from programs that send elsewhere, that a path lies in one of Plainva's folders. It learns that such a note exists at the path it named itself — which it could have found out by listing the folder.
- External agents have met no agent but the scripted one of this repository. The terminal for a sign-in ran on Windows in a test of its own; the Linux path is compiled and its parts are tested in CI, but it never opened a terminal on a desktop; the macOS path is first compiled by a release build.
- A sign-in to a foreign server has only ever been made against the scripted authorization server of this repository. Plainva's description as a client is a document on the project's website: whoever can change it can add ways back for "Plainva" at authorization servers that read it. Signing out forgets the tokens on the device and does not ask the authorization server to end them ([review](MCP_Client_Security_Review.md), question 9).
- What the system's assistant does with a title it was allowed to read is not Plainva's to see: where it processes it, whether it hands it to another assistant or a search, how long it keeps it. The system also keeps copies of its own — of the notes it offers for a spoken phrase, of a note a saved shortcut names; Plainva tells it when the list changed and cannot check that it forgot. That is why the list is off until chosen, and why the switch says that what the system does with a title is not Plainva's to control.
- The list follows the vault by one pass. A note marked as kept from the cloud a moment ago is still named until the list is written again: a moment after the save, and at the latest as the app leaves. A rule that arrives through sync while the app is closed reaches the list when the app next runs.
- Titles and folder names lie as a file in the App Group container: readable by the app and its extensions, not while the device is locked, and not part of a backup. A key travels further — the system keeps it as a note's identity, and a shortcut somebody shares carries it together with the title its author picked. Without the device's secret a key says nothing about where a note lies; the title in a shared shortcut is the author's own to give away.
- What is said to the system's assistant is the system's to process, by the person's own act, and then lies as text in the orders file until the app opens. Whoever can speak to a device that counts as authenticated — unlocked, or vouched for by a watch or a car — can dictate an entry or a task; it arrives in the vault as the person's own words, unmarked.
- A task dictated to the system is created from its words alone, read like a line typed into the capture field: nobody confirms the date that was understood or the list it is sent to.
- No intent has run on a device or with Siri. The Swift store and matcher are tested by a compiler run in CI and the web layer against a fixture bridge; how the system understands the phrases in ten languages, and what it shows and keeps, is unseen ([architecture](System_Assistant.md), "Not verified").
