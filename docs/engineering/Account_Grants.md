# Device-local account grants and Drive destinations

Updated: 2026-10-12

Gmail, native Android renewal and test-client configuration: [Native Google mail](Google_Mail.md).

An account may retain several independently issued grants. A grant records its client registration, the provider's actual scopes and a verified provider subject. Selecting a grant requires one grant to cover the requested service; permissions from two tokens are never combined to manufacture permission neither token has. Microsoft mail participates in the same consent planner as files and calendar. Adding a service requests the selected service's permissions and keeps existing grants after cancellation, incomplete consent or an identity mismatch.

`accountCredentials.ts` defines the backwards-compatible credential document; `accountGrantMigration.ts` imports legacy service credentials. Both shell adapters use compare-and-set in native secure storage. A successful rotating response is persisted to its source before identity validation and account adoption. Account storage is confirmed before clearing the legacy refresh token. An interrupted adoption resumes from the confirmed copy without another browser consent. Storage failures preserve the source, and stale writers cannot replace a newer login. The broker owns subsequent refreshes; service bindings retain their non-secret configuration. Credentials remain device-local.

A calendar account or a mailbox asks the broker for its own card. The asking account is a required part of the question, and only a card whose service reference points at exactly that account may answer (`packages/ui/src/lib/accountBrokerLookup.ts`, one rule for both shells). No such card means no broker: the service uses its own sign-in, never another account's. Until 2026-10-12 both shells registered the mail resolver without the mailbox, so the first card that carried mail answered for every mailbox of a vault, and a second Microsoft mailbox read and sent as the first account — Graph answers `/me` for the account of the token. A mailbox that falls back keeps working when its own slot holds a sign-in. A slot is emptied only by a step that at that moment holds or writes a card pointing at the same mailbox; the automatic fold of duplicate cards can remove that card later and leave the mailbox row without one, and such a row asks for a sign-in instead of borrowing the surviving card's. While the desktop connects an account, the sign-in of that connect — just minted, or the one of the card it reuses — answers the one mailbox the connect creates and names (`claimPendingMailbox`), not every mailbox no card claims yet; the phone validates with the access token it holds and binds the card in the same step. File sync is not asked this way: a vault syncs through one account, which names its provider and client (`fileBrokerBinding.ts`), and two usable candidates are ambiguous rather than first-come.

OneDrive and Dropbox targets hold an uncommitted rotating response until persistence succeeds. A retry confirms that response before using its access token instead of requesting another rotation. A token's reported scopes are checked again after refresh. Microsoft refresh tokens are bound to the user and client, not a single resource; this does not establish that an arbitrary access token grants mail, files or calendar rights. See [Microsoft refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens).

An explicit Drive destination is stored as `{ path, id }` in the existing device-local folder setting. Historical string settings remain readable. Both shells preview the current and proposed folders, identify same-named folders by ID and require confirmation. Preview reads bounded metadata only. The chosen ID is checked again before confirmation and before every sync pull, including cursor pulls. A deleted or unavailable root is an error, never an empty remote. No folder is moved or deleted by this selection. The profile connection fingerprint includes the ID. See [Drive files](https://developers.google.com/workspace/drive/api/reference/rest/v3/files) and [listing](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list).

Validation covers interrupted migration, false identity, incomplete grants, concurrent secure-store writes, reconnect after rotation, expired consent, same-named destinations and disappearance of a cached root. A native Windows two-window probe observed one successful compare-and-set and one rejected stale writer. The shared destination dialog was exercised in the isolated Windows app and at 320 pixels in the mobile browser with fictional folder metadata. These probes do not claim a live Google or Microsoft account was used.
