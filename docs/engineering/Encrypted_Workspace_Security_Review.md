# Encrypted Workspace Independent Review Record

Last reviewed: 2026-09-04

Status: **BLOCKED — independent review not yet performed**

This is deliberately not a self-attestation. An independent reviewer must inspect the protocol and threat model, HPKE use, signatures and chain validation, AEAD framing/AAD, recovery/owner-transfer ordering, revocation/full rekey, published-slice isolation, and provider faults.

Surfaces added since 2026-07-23 that the review scope MUST also cover: the invitation codec (`PVINVITE1`) and the offline QR representation of invitation and pairing tokens (a QR must carry no more authority than the copyable text, and reading it must not skip the fingerprint comparison); the device-local decommission and the fail-closed orphan reset (neither may downgrade an encrypted connection to plaintext without explicit confirmation); and the boundary between the content-E2E "reset encryption" and the workspace decommission. And the global "lift encryption" action (`liftWorkspaceEncryption`, shipped 2026-07-23), which an earlier version of this record wrongly called unimplemented: it tears the workspace runtime down like a decommission and reopens the SAME cloud folder as a plaintext connection that re-uploads every local file. Two things the review has to weigh there: the action deletes nothing — the immutable `.pvws/` objects stay until the user removes them by hand, so ciphertext outlives the decision while its keys do not — and it is reachable only behind an explicit confirmation.

And, since Stufe B (2026-08-31), **publication** as a scope item of its own: a slice handed to people outside the vault becomes a SEPARATE encrypted workspace with its own genesis, its own owner group and its own recipient group, written under `.pvws/publications/<id>/` and derived so the folder name discloses neither the main workspace nor the slice. Five things the review has to weigh there. **One**, the isolation claim itself: a recipient key must open nothing in the vault the slice was cut from — `packages/core/test/workspace-publication.test.ts` asserts the refusal AND keeps a permanent counter-probe that the same frame opens with the main vault's own key, so the assertion cannot pass because every decrypt fails. **Two**, unlinkability across publications: the same note carries a different published object id in every publication, so a recipient of two slices cannot learn that they overlap. **Three**, the projection: a sanitized publication strips private frontmatter, neutralizes links to excluded notes and omits excluded embeds BEFORE anything is sealed — the publishing path never sees the source note, which is the property that makes "exact or sanitized" enforceable rather than advisory. **Four**, withdrawal: revoking a recipient rotates the recipient group and makes the next key epoch unreadable for them, but retrieves nothing already copied; withdrawing a whole publication tombstones every object and clears the key LAST, because the tombstones need the runtime that the key unlocks. **Five**, the guard that stops a publisher revoking their own Owner out of a publication — a red probe showed the underlying governance call throws nothing without it, which would leave a publication with no one able to administer it.

And, since 2026-09-04, the **acceptance rule for operations** — a change at the security boundary, made because the previous rule was broken in the other direction. Until then an operation was accepted only if it referenced the NEWEST policy version, which refused every operation older than the last policy change; because objects are materialised only while applying an operation, a device joining after any policy change rebuilt the vault empty, and the vault that surfaced this had 176 of 181 operations in quarantine. The rule now follows the protocol: the referenced version must be on the accepted chain and the capability is evaluated in it. Three things the review has to weigh. **One**, that this is the protocol's own wording (§ 2.2, § 17.1) and not a relaxation invented here. **Two**, the replacement for what the defect accidentally blocked: a device revoked in the current policy is heard only up to the sequence an ACTIVE device last witnessed for it in a signed checkpoint, its pointer file is ignored, and anything above the line is refused as post-revocation — the reviewer should judge whether a checkpoint-derived line is the right anchor, and whether the explicit per-device `revokedAtSequence` noted for the next protocol version should come sooner. **Three**, the chain rule that came with it: per-device chains continue from what the reader already holds instead of demanding sequence one, and operations already applied are not re-judged — the reviewer should confirm that "already applied" (an operation hash in the local store) cannot be reached without having passed every check once.
