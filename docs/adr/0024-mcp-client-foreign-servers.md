# ADR 0024: The MCP client — foreign servers approved by content, used per vault, asked per call

Status: Accepted

Date: 2026-10-07

## Context

[ADR 0022](0022-mcp-server-without-a-network-port.md) decided both directions of MCP in outline and built the first: Plainva as a server for AI apps on the same computer. This ADR records the second as it was built — Plainva's assistant using tools and prompts of servers the user connects — and replaces §8–10 of ADR 0022 where the two differ.

A foreign server is somebody else's program or service. It speaks to a model through four channels — its instructions, its tool descriptions, its prompts and its results — and every call hands it data. The incident that shaped the design: a server answered three calls honestly and then rewrote its tool list and a prompt, so that the agent went looking for credentials (Pillar Security, 2026-08-12).

Three constraints came from the rest of the harness. Keys and addresses never live in the WebView ([ADR 0017](0017-ai-harness-architecture-and-native-boundary.md)). A conversation's tool list is fixed when it starts, and everything else is reached through the tool search ([ADR 0019](0019-ai-tools-risk-classes-and-approvals.md)). And nothing becomes active by arriving: an approval is per device, bound to content, and stored outside the vault ([ADR 0020](0020-ai-skills-memory-and-script-skills.md)).

## Decision

1. **An own protocol client, behind native ports.** The protocol — both generations, the stateless revision of 2026-07-28 and the earlier ones with a handshake — is a thin client in `packages/core/src/ai/mcp/`. It never opens a socket or starts a process: requests and programs are two ports the shells implement natively. This replaces "the official TypeScript SDK" of ADR 0022 §8. The SDK would have put the transport, the address and the credentials into the WebView and brought capabilities Plainva deliberately does not offer; the part of the protocol a client needs that offers a server nothing is small enough to own and to test against a scripted server.

2. **Plainva offers a server nothing.** No roots, no sampling, no logging, no elicitation, no subscription stream. A server that asks the user for something gets an error and no dialog. A list is loaded again before a use instead of being pushed.

3. **Three places for three decisions.**
   - *Native, per device:* where a request goes or what is started, and the credentials. A server is registered only through the system's own dialog, which shows the address or the whole command line; afterwards the WebView names it by an id.
   - *App data, per device:* the user's name for the server, the approved listing and its pin.
   - *App data, per vault:* whether the vault uses the server, which tools it granted, which folders it allowed, and a log of calls.
   Nothing is stored in the vault. An approval and a vault's choice are bound to the registration; a server registered anew under the same id is new everywhere.

4. **An approval covers texts, and is checked before every use.** The pin of ADR 0022 §9 is enforced at two points: the review, and a reload before each call or prompt (a server's own freshness hint counts for at most five minutes). Any difference blocks the server until the user looks again; flipping back does not unblock. What a conversation reads of a server comes from the approved snapshot, never from a connection.

5. **Foreign tools are never a provider's tools.** They are names in the conversation's list of further tools (`mcp_<server>_<tool>`, the server id chosen by the user), found through the tool search and called through the dispatcher. What the search says of them is built from the snapshot and stands in the untrusted-data block. A server's `instructions` are shown at the review and go to no model.

6. **One call, decided in the order of trust.** The server and the tool as they stand now; the listing against the pin; everything the conversation has read from the vault against the folders the vault allowed this server — none by default — and against the privacy gate, where every foreign server is a cloud recipient, a local program included; and last the user, who sees the server, the tool and the arguments in full. A yes is for one call. There is no "always".

7. **A tick is for what a tool said it does, and a tool that changes something is asked about in other words.** What a tool may do at its service is the server's own claim, read the cautious way round: only `readOnlyHint: true` *reads*; a tool that says nothing may *change, overwrite or delete*; `destructiveHint: false` narrows that to *may change*. Every tool can be ticked in a vault, and none is ticked by default. A tick records the effect the tool declared when it was set, and a call is held to it: a tool that says more later is not offered until it is ticked again, so a yes to reading never becomes a yes to changing. A call of a tool that does not only read passes the same chain (decision 6) and is then asked under a heading of its own, with the sentence that Plainva cannot undo it and a button that is not the dialog's obvious one. The claim decides which words the user reads — never whether they are asked. Nothing a foreign tool does or returns changes the vault. *(First built as "only reading": a tool that did not declare itself read-only was not offered. Opened on 2026-10-07 with the approval chain of ADR 0019, risk class `external`.)*

8. **Nobody's conversation gets none.** A conversation bound to a skill, a door, a regression run and the system's own model reach no foreign tool.

9. **Prompts are the user's step.** A prompt is started by the user from an empty conversation. An expansion nobody approved is shown in full and pinned when it is sent; the same one goes directly afterwards; another one blocks the server.

10. **Programs only on the desktop, without a shell.** A stdio server is started from the registry's entry, with a short environment, in a sandbox where a self-test on this computer says it holds, and it ends with the app or after ten minutes without use. A phone starts no programs.

11. **A sign-in is made natively, and a token is for one server.** Where a remote server wants a sign-in, Plainva signs in with OAuth 2.1 and PKCE in the system's browser — ADR 0022 §10 as built. The WebView finds out where the sign-in lives, opens the browser and hands back what it returned with; the verifier, the exchange of the code, the tokens and their renewal are native, and no command answers with any of them. The endpoints a code and a token are sent to come from a document the native side fetched itself, from the authorization server's own origin and with the issuer it was asked as inside — so a WebView that was taken over cannot pair a real authorization endpoint with a token endpoint of its own. Who answered is checked against who was asked (RFC 9207) before anything of the answer is used. A token is asked for the registered address, or for the part of it the server names as itself (RFC 8707), and goes to that address only. To an authorization server Plainva is, in this order: the client it was before, the address of its own description (`https://plainva.com/oauth/client.json`), a registration it makes itself, or an id the user was given. An authorization server that does not say it does PKCE with SHA-256 is refused. A server has one credential: a sign-in and a stored token replace each other.

## Consequences

- The protocol client is Plainva's to maintain: a new revision of the specification is work in `wire.ts` and its neighbours, with the scripted server as the test bed.
- A user answers a question for every call. That is the price of not having an "always", and it is why looking for tools asks nothing.
- A conversation that has read notes outside a server's folders cannot use that server at all, until the user allows the folders or starts a new conversation. The refusal says so.
- What a foreign tool changes at its service is outside Plainva: there is no undo, no suggestion round and no draft for it, and the question says so. A server that describes a tool as harmless and deletes with it is not caught by a declaration — the user's look at the tool, its description and the arguments is the control, as it is for what a call carries.
- Signing in depends on one document outside this repository: Plainva's description as a client is part of the project's website (`/oauth/client.json`), and what it lists is pinned by a test here (`mcpClientDocument`). Until it is published, an authorization server that reads it refuses the sign-in in the browser; a registration and an id from the server's operator do not depend on it.
- Three native implementations hold one contract, the sign-in's rules included: one list of cases per rule runs on all of them and on the reference in TypeScript. A source-level test keeps the rest aligned; only CI compiles all three.

## Alternatives

- **The official SDK in the WebView.** Rejected: see decision 1.
- **Foreign tools in the provider's tool list.** Rejected: a tool list is part of every request, so a description a server controls would sit beside the system prompt in every turn, and adding a server would change the cache key and the approved scope of every conversation.
- **Approve a server once, by its address.** Rejected: an address says who answers, not what they say. The incident above was a server whose address never changed.
- **"Always allow" per tool.** Rejected for now: with private notes in a conversation and a stranger's text in the same run, a standing approval for a way out is the third leg of the Rule of Two.
- **Check only the paths that appear in the arguments.** Rejected: arguments are text a model wrote, and a model can write anything it has read into them. What counts is what the conversation could carry.
- **One switch per server, "may change things".** Rejected: it would allow tools nobody looked at, and a tool added to an approved listing later would inherit it. The unit of a yes stays the tool, and the effect it declared.
- **Let the annotations decide more than wording.** Rejected: they are a server's claim about itself. A claim to only read gets the ordinary question, a missing claim counts as the protocol's own default — the worst case —, and no claim removes a question. A server gains nothing by leaving the annotations out.

## Deferred, and why

- **Elicitation** (a server asking the user). A server that may put its own words into Plainva's dialogs has a phishing channel; this needs a design of its own, with the approval chain. Built on 2026-10-25 — see the addendum below.
- **Skills offered by a server.** They would go through the content-bound approval of ADR 0020; nothing reads the extension yet. Built on 2026-10-25 — see the second addendum below.
- **A stream of notifications.** Reloading before use covers the security case; a stream is an optimisation.
- **Around the sign-in.** Asking an authorization server to revoke a token when the user signs out (the tokens are forgotten on the device), asking for more scopes on its own when a server says a sign-in does not allow something (the user signs in again), and a client with a secret of its own.

## Addendum 2026-10-25 (questions to the user)

Plan P9-4a, from the deferred list above. Some servers need a detail from the user during a call — which project to search — or want the user to sign in at a third service they reach for them. The current revision of the protocol lets a server ask within a request: it answers a call or a prompt with an unfinished result and its questions, and the client sends the same request again with the answers (multi round-trip requests). That is the whole channel; the decisions are about who may use it and how its words are shown.

1. **Offered per server and vault, off by default.** A grant has a field `questions` (the review's **Let ⟨server⟩ ask you questions**); a grant without it — every grant from before — allows no questions. Only where it is set does a call or a prompt of that server declare `elicitation` in its request's capabilities, and only in the stateless revision: an earlier one would ask on a stream of its own, which is not offered. Everywhere else the capabilities stay empty, and a server that asks anyway is not followed: the call fails, nothing it asked is shown, and the model is told that the user can allow questions in the server's settings. A server that says so with an error instead — `-32021`, a capability it needs, the protocol's own way — is read the same. A server of an earlier revision is offered nothing, and its review says so instead of offering the box.
2. **Plainva's card, the server's words as a quote.** A question stands above the composer where the question about a call stands, in the same dress (`AiMcpQuestion`). Its title, buttons and hints are Plainva's; what the server wrote — its message, the titles and descriptions of its fields, the labels of its choices — stands inside as the server's quote, cleaned of invisible characters, folded and cut, rendered as text, never as a title or a button. A server cannot ask anything that looks as if Plainva asked it.
3. **Forms Plainva can show, and nothing else.** A form is a flat object of text (with the formats email, uri, date, date-time), number, whole number, yes/no and a choice of one or of several — or no field at all, which asks the user to confirm. What is anything else — nested, an unknown type or format, more than twenty fields, more than fifty choices, a choice twice, a field named like a property every object has — is not shown: the server gets a no, and the card says that it asked in a way Plainva cannot show. An answer is checked against what was asked before it goes — a number as the user's language writes it, with no guessing at "1,000"; a day that exists — and once more on its way out.
4. **No question for a secret.** A server must not ask for a password, a key, a token or payment data in a form. Where a form has a field to type into, what says what to type — the field's name, title and description, and the question — may not name one even in a word that has other meanings ("token", "PIN", "TAN", "cookie"; `accessToken` counts as two words, full-width and decomposed letters as the plain ones), and nothing around it — a neighbour, a choice — may name one in so many words ("password" also inside "Einmalpasswort", "API token", "card number", plurals included, in the app's languages). In doubt a form is refused: a server asking to name a new API token is refused with one that asks for it. Such a form is not shown: the server gets a no, and the card says what it asked for. A form without a field to type into is shown: nobody types a secret into a yes or a choice. The words are a heuristic; the protocol's rule and the hint on every card ("never enter a password or a key here") stand behind it.
5. **A page opens on a click, in the system's browser.** A question may ask the user to open a page. Plainva opens only https, a page on this device only for a server on this device (and there http as well) — a remote server does not send the user's browser to the user's own machine —, and no address that carries a sign-in of its own; it shows the whole address with its host apart, warns where a host is written in punycode or is a bare IP address, and opens it only on **Open in browser**, once: on the desktop in the default browser, on the phone in the system's browser view, never in the app's web view. The server hears yes only on **Continue**, after the user came back; nothing is fetched before.
6. **The answer goes to the server alone.** No model sees a question or an answer: the model gets the call's result. The record of a run counts the questions of a call the user saw and how each went — answered, declined, stopped, refused by Plainva —, never what was asked or answered. A prompt whose expansion depends on what the user answered is pinned under its name, its arguments and a hash of what went to the server — every answer, the ones nobody was asked for included: another answer may expand to another text and is shown first, like any expansion nobody approved yet, instead of blocking the server. The hash lies with the approval in the app's data on this device, never in the vault; a server keeps at most 200 pinned expansions, and the oldest goes first.
7. **Bounded.** At most five questions in one round and three rounds per request; a server that asks more is not followed. Questions come one at a time — a second one waits for the first, it never takes its place —; an answer is given to the card it was asked on, and a page is said yes to only once it was opened. After a no or a stop, the rest of the request gets the same answer without being shown; one card per request says that Plainva refused a question, the next refusals go unshown. A connection that waits for an answer is not ended for being idle. STOP, another conversation, another vault and the device turning fully local stop the question and the call or the prompt: a prompt that was stopped sends nothing, and after a no its expansion is read before it goes. A question that comes while nobody is looking brings the conversation forward, as the question about a call does. Routines, doors and regression runs reach no foreign server and so no question.
8. **Still not offered:** a model call for the server (sampling) and the roots of the file system. A request that asks for either fails as before.

## Addendum 2026-10-25 (skills a server serves)

Plan P9-4b, from the deferred list above. A server can serve skills — instructions for its tools in the Agent Skills format — through the MCP skills extension (`io.modelcontextprotocol/skills`, SEP-2640): it lists each with its frontmatter and a manifest of its files (address, SHA-256, size), answers for one by its address, and serves the files as resources. A skill is the strongest text a server can bring into a conversation — instructions the model follows —, so everything turns on the approval being bound to exactly what was seen, and on nothing of it counting for more than the user decided.

1. **Read only where it is declared, kept on this device.** A server serves skills when its discovery declares resources and the extension, in the stateless revision — read again with every listing, so that a server that begins or stops serving skills is followed at the next look. Whenever Plainva loads a server's listing — the review, the look before a use — it reads its skills too (`skills/list`, and `skills/get` for each address the user added by hand), and keeps what the server listed with the server's record on this device. The addresses the user added come first, so that a long list never pushes one out; a reading that fails keeps the list before it, shown as of when it was read; a server that no longer declares the extension keeps only those addresses, for the day it serves skills again. A registration anew is another server: its skills go. Each entry is checked as the extension writes it: an address of a `SKILL.md`, whose folder's last segment is the skill's name, and that — like the name it gives the skill, read after percent-decoding, and every path of its manifest — hides nothing a person cannot see (no control, format or ignorable character, no separator; fillers that count as letters are ignorable too) and — the address and the paths — writes no markup (`<`, `>`, quotes, the backtick, look-alike brackets): a name and a path are shown in the review and written into Plainva's own words to a model; a frontmatter map; a manifest that names `SKILL.md` once and every file once, inside the skill's folder, with a lowercase `sha256:` digest and a size; at most 512 files and 16 MiB, which Plainva carries, and a `SKILL.md` no larger than a skill of the vault may have (64 KiB). Two skills whose names fold to one key (NFKC, lower case) are both marked and neither can be approved: a name is a label, and which of the two a model meant, nobody could tell. What is kept of one server's skills is bounded as well (about 4 MB as JSON): an entry too large on its own is kept as too large, without its manifest, and beyond that the last entries go and the list says it is clipped. A skill with generated content (`"dynamic"`) has nothing an approval could bind to, and Plainva declines it; what does not read stays visible with what is wrong with it, never approvable.
2. **Nothing is read ahead.** No file of a skill is read when the server is connected, when its list is read, or when the skill is approved: the review shows the manifest. A file is read when a conversation loads the skill, or when the user asks to see its instructions — and then it is checked first.
3. **Approved like a skill of the vault, bound to every file and to what the server says of it.** The approval lies in the same store as an own skill's — per vault, on this device, never in the vault — and binds every file of the manifest by path and digest, and the SHA-256 of the listed frontmatter as canonical JSON (the catalog describes the skill with what the server lists, so a new description is a skill to look at again). Any change to either — a file added, removed or changed, another description — lifts it, and the review of the new version lists what changed. **Show instructions** reads the `SKILL.md` and each file a model may read — at most twenty files and 1 MiB at one look —, each checked, and says of a file it does not show why (too large, other bytes, no text, no answer now, beyond one look); a reading of another version than the review shows says that the skill changed. Where the user read the instructions before approving, and they are exactly the approved `SKILL.md` (a byte order mark in front included), the approval keeps them, so that the review of a later version compares the new instructions with them line by line. The identity is the server as this device calls it, its registration — what is registered and when it was added, so that a server removed and added again at the same address is another, and the approvals of its skills in other vaults do not come back with it — and the skill's address; the name is a label. Removing a server removes the approvals of its skills in the open vault.
4. **Apart from the vault's and the app's skills.** A server's skills stand in their own part of the session's state, so that nothing that reads the vault's and the app's skills — routines, doors, regression runs, learning, the hints, the chips and the palette — sees one. They are offered only in a conversation the user begins — never in a door, a routine, a regression run or a conversation bound to a skill — and only from a server that is ready in the vault (approved as it lists itself, registered as it was approved, switched on there), never while the device is fully local. Whether the vault grants any of the server's tools does not matter: a skill can work with Plainva's reading tools alone. In the catalog they stand after the user's own skills in a fence of their own (`<server_skills>`) with a budget of their own, so that a server never pushes the user's skills out; each under the key `mcp_<server>/<name>`, which no skill of the vault or the app can have, with its description quoted as the server's words — no bracket of a tag left in it, only its escape. A conversation is never bound to a server's skill: its instructions do not enter the system prompt.
5. **Loaded only checked, with its server named.** `use_skill` reads the `SKILL.md` from the skill's own server, after the same look at the server as before any use, without offering questions: its bytes must have the manifest's size and digest, be UTF-8, be a skill the format accepts, and say of themselves, field for field, what the server listed. What passes enters the conversation as a tool result that names the server and says its words are not the user's, in a block marked `origin="server"` that no text inside it can close or open another of — every tag of the blocks in it is escaped as a reader would read it — each character in its compatibility form without marks and in lower case, or as the letter it only looks like (small capitals, Cyrillic, Greek and Armenian look-alikes, enclosed letters), brackets and slashes that look alike, an underscore written otherwise or left out, and blanks, controls and characters that show nothing anywhere in it skipped —, as the data fence escapes its own (`defuseTags`); the fence's origin and the catalog lines of the user's own skills take no tag either. A look-alike the list does not name is not caught: the tags are not secret, and what holds beyond them is the rule of the fence and the bound of what a skill may use. Its frontmatter is found as every properties block is, between fences on lines of their own, and a `---` inside a line of it makes the file unreadable — other tools end the frontmatter there and read other fields; a main file whose frontmatter does not read is invalid, not one that says otherwise: what the review shows as the header is what is read as it, and nothing is read two ways. A file of the skill is read the same way, only by a path its manifest names, only from that server, at most 1 MiB, and reaches the model inside the fence of untrusted data: the server's data, never instructions. Content that fails is not used, and the entry is read again so that the review shows the skill as changed. Verified bytes are kept in memory by their digest, at most 32 MiB, and go with the server; nothing is kept on disk.
6. **What it may use comes from where it comes from — for the rest of the conversation.** The extension says a host must ignore a skill's `allowed-tools`, and Plainva ignores its own fields in `metadata` as well. A server's skill gets Plainva's tools that only read or show — not the app's commands, not the internet, none of Plainva's tools that write, no script — and the tools of its own server the vault granted, each call asked as always; never another server's tools, so a skill of one server does not drive calls to another. The moment words of a server's skill — its instructions or one of its files — enter a conversation, that bound holds for the rest of it: in the same run and in every later one (a run records the skills it loaded), whichever skill is loaded after — a skill of the vault loaded later gets only what both allow, and one loaded before is held to it from then on, so that every reader of the run's bound (the executor, the tool search, the question about a page) reads the same. A later run learns of it from the conversation itself — the skills its runs recorded, and the calls of `use_skill` in it, through the dispatcher too —, and allows the tools of the skill's server only while that server is registered as it was then. The tool search lists, of foreign tools, those the bound leaves: a server's skill finds its own server's. The review says so, and names the tools a skill lists for itself as counting for nothing.
7. **By its address.** The extension asks a host to load a skill by its address, listed or not: the workshop's **Add by address…** asks the server for that entry (`skills/get`), keeps the address with the server on this device — sixteen at most — and asks for it at every reading; an address the server no longer knows goes.
8. **Still not offered:** reading a skill's folder live (`resources/directory/read`) — the manifest is the whole of a skill —, skills with generated content, a skill nested in another activated through it, and a skill's scripts: a server's skill runs nothing.
