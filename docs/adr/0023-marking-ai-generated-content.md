# ADR 0023: Marking AI-generated content (EU AI Act, Article 50)

Status: Accepted

Date: 2026-09-24

## Context

Article 50 of the EU AI Act applies since 2026-08-02. It asks that people
know when they interact with an AI system, and that synthetic text, audio and
images be marked in a machine-readable way and detectable as artificially
generated. Building on third-party models does not move that duty to the model
provider, and open-source software is not exempt. The Commission's guidelines
treat grammar, spelling, minor style fixes and translation as "standard
editing"; summaries and substantial rewrites are not. Only systems placed on
the market before 2026-08-02 have until 2026-12-02 for the machine-readable
part — the harness ships later, so it marks from its first release.

Plainva writes AI output into the user's own Markdown files, which other tools
read too. A marking must therefore survive outside Plainva where it is
machine-readable, and must not litter notes in a way that breaks Obsidian
compatibility or misattributes human text.

## Decision

The harness marks conservatively — everything it generates or rewrites,
standard editing included — until a legal review says a narrower rule is
enough. The review runs in parallel and does not block (E33).

1. **In the conversation.** Every assistant message carries its origin
   ("Plainva KI · ⟨model⟩"), and every new conversation starts with a one-line
   notice that answers are generated by an AI model and may be wrong.
2. **Proposals.** Every text change, transcript and property value the
   harness proposes is a suggestion round with the author
   `plainva-ai/<model-id>`, shown as "Plainva KI · ⟨model⟩" (ADR 0019). The
   author stays in the suggestion history after the user accepts the round, so
   the record of which passage an AI wrote survives the acceptance. Proposals
   from other harnesses carry `mcp:<client>` or `acp:<agent>`. A reply the
   assistant writes into a comment thread (addressed with "@AI") is a remark
   under the same author and is shown with the AI mark in place of initials;
   it is never text in the note.
3. **New notes.** A note the harness creates carries OKF provenance in its
   frontmatter — `generated: { by: "plainva-ai/<model-id>", at: <ISO-8601> }`
   and, where it answered from the vault or the web, `sources` — written once,
   at the moment of creation, through the OKF write path (ADR 0009). This is
   the machine-readable marking that travels with the file into every other
   tool, export and publication. The first such note is an answer the user
   keeps as a note (ADR 0019 §11): besides the stamp, its first line says in
   words that an AI wrote it, with the model, the time and the question, so
   the marking is also there for a person who reads the file anywhere else.
   Nothing sets `verified` on it.
4. **No note-level marking for passages.** An accepted change inside an
   existing note does not stamp the note: a note-level flag cannot say which
   passage the AI wrote and would mislabel the human text around it. The
   passage-level record is the suggestion history (item 2).
5. **Encrypted workspaces:** the harness makes no proposals and writes no
   replies there until the sealed comment path carries the author field
   (ADR 0017), so the marking can never be lost in that path. An answer kept
   as a note is written there like any note, through the workspace's own
   adapter chain with the member's rights: its marking stands in the note's
   own frontmatter and first line and travels with the note.
6. The OKF trust fields are a critical write class (ADR 0019): the harness
   can never write `verified` with a `human:` actor or remove a `generated`
   stamp.

## Consequences

- Notes created with AI help are recognisable by any OKF-aware tool; text the
  AI changed inside a note is recognisable in Plainva through the history.
- Conservative marking labels standard editing too. If the legal review
  confirms the standard-editing exemption, rule 2 can relax for grammar,
  spelling and translation — the author field stays either way.

## Alternatives

- **Inline markers in the Markdown** (HTML comments around AI passages).
  Rejected: they break the "plain Markdown" promise, survive edits
  incorrectly and appear as noise in other editors.
- **A note-level `ai: true` flag.** Rejected: it cannot tell which passage is
  generated, and it would stay on a note a person later rewrote completely.
