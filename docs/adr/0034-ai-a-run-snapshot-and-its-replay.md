# ADR 0034: A run's snapshot is its own line, kept as versions — and the same question can go to another model

Status: Accepted

Date: 2026-10-25

## Context

The plan's "context snapshot" (§ 18) asks for what made an answer — the request, the context package, the sources with hashes, the skill's version, provider and model, the tools, the rules, the result and what it changed — and for a **provider replay**: the same context asked of another model.

Most of it is kept already. Each run of a conversation has a record (`RunMeta`): its user turn, provider and model, the notes its context carried and the ones a rule kept back, its usage, its steps, its send overview (the manifest: each source by path, section, tier and reasons), the skills it used, what it asked of the internet, of mail, of foreign servers, the notes its tools read, the rules that passed and what it left for the user — suggestion rounds, drafts, plans. The line under each answer already opens that record as the send overview (ADR 0018). What is not kept is the version of what went: whether a note still reads as it did for the answer cannot be told.

## Decision

1. **The snapshot is the line that is already there.** Opened, the line under an answer shows the send overview as before, and beside it the run's snapshot: when it was asked, each source with its version and how it reads now, the notes the run's tools read with theirs, the tools it called and how often, the version of each skill it used, and what it left. No surface of its own: the same component in both shells (`AiSendOverview`, filled by `AiRunOverview`).

2. **Versions, never text.** A version is the SHA-256 of a note's text as the run read it — for the context package, every note it read for evidence or a card (`PackageRef.hash`, carried into the manifest's sources); for the tools, every note a tool was given whole (`RunMeta.readHashes`, through the gate's `passed`, which now gets the text where the tool had it). A handle of the context map read nothing and has none; a note a search only found has none. A skill's version is the SHA-256 of its `SKILL.md` as the scan saw it, for the bound skill and for every one the model loaded. The record keeps these hashes and paths, never a word of a note; read back, anything that is no hash is dropped.

3. **"Changed since" is asked when the line opens, on this device.** Each kept version against the note as it is then: **unchanged**, **changed since**, **no longer there**; a skill against its `SKILL.md` now. Nothing is sent, nothing is stored. A changed line end is a changed text: the version is what the run read.

4. **Asking another model is a new conversation, begun as the user would begin it.** "Ask another model…" asks the run's words again of a model the user picks from the profiles of this device — not the one that answered, and while the device is fully local only one on it. The new conversation pins exactly the notes the run's context read, takes nothing a search would find besides them (`pinsOnly`), leaves the note that happens to be open out, binds the skill the original was bound to where it is still active, carries the vault's memory and tools as any conversation does and the internet where the original had it and the vault allows it now. It says where it comes from (`ConversationRecord.replayOf`: the conversation, the run, when, which model, how many of its notes changed since) and offers the way back to it.

5. **The gate holds as it holds now, and the send overview asks as always.** A note the rules keep from the chosen model now does not go, even if it went then; the overview counts it as kept back. A different provider or model is a growing scope (ADR 0018): the overview asks before anything is sent.

6. **Two limits.** Only the **first question** of a conversation is asked again: a later one rests on what was said before, and that history carries text that was put together for the original's reader — a model's answers that quote notes, results of tools — which a replay could not gate again without rebuilding it. And only a question that brought **nothing but notes** beside the user's words: the material of a door (a selection, a picture, a recording, a comment thread, a database's columns) and of a folder's log is not kept to bring again. The line says why where it offers nothing.

7. **No verdict.** Plainva does not compare the two answers; both conversations stand side by side in the history, and the replay names its original.

## Consequences

- A snapshot costs a hash per source and per note a tool read — a few dozen bytes each, bounded like the paths of what was read (`RUN_READ_CAP`). Older records have no versions; their lines show what they always showed.
- "Changed since" reads each kept note once when a line opens. A conversation with many sources opens a little slower; nothing happens before the line is opened.
- A replay sends the notes as they are now, not as they were: the record keeps no text to send. A source that changed is said in the line before the replay and in the replay's head.
- The model chosen for a replay is one of the device's profiles: a model that is set up but not in a profile is not offered.

## Alternatives

- **Keep the texts that went.** It would make a replay exact — and the history a second copy of every note a model was shown, kept beside the vault and outside its rules. Rejected: versions tell whether something changed; the vault keeps the texts.
- **Replay the whole conversation.** It would ask later questions too. The history holds answers and tool results put together for the original's reader; sending them to another model would need every one of them gated anew for that model, and an answer that quotes a note the new model may not see cannot be cut without changing it. Rejected for now; the first question of a conversation is what most comparisons need.
- **A comparison view.** Two answers side by side, with what differs marked. Not built: two conversations already stand side by side, and a mark of "what differs" in prose would be one more judgment the app makes.
- **The skill's whole folder as its version.** A skill's other files are loaded one by one and seldom; `SKILL.md` is what every bound run carries. The version is that file's.

## Addendum 2026-10-26: what a run writes of its conversation

A run took its conversation as it began and wrote it back so when it ended. A title, a pin, a redaction or a model chosen while the send overview was open or the answer on its way was gone again afterwards — a redaction with it, so that the next message sent the note whole; a choice made meanwhile was stored onto the run's unfinished turns; and a conversation the user deleted meanwhile came back.

1. **A run writes what it owns:** its turns, its usage and its record, when it ends. The title, the pins, what goes redacted and the model of the next message are the user's; the run takes them from the latest choice it carries — every choice reaches the run the moment it is made, on screen or from the history (`withUserChoices`). From the run's end until it is decided what the screen and the history show of it, a choice goes onto the conversation with the run's turns and record in it, whatever the screen still shows.
2. **A choice made while a message is on its way** — from its send overview to the end of the answer — counts from the next message on: the message goes as the overview showed it. Made while the overview is open, the run takes it along when it starts (`withScreenChoices`; what the overview itself took in or out of what goes redacted counts on top). Made while the run is on its way, it is on screen at once and goes onto the conversation as it was stored before the run, never onto the run's unfinished turns (`storeChoice`); a conversation the run began is in no storage until the run ends and takes the choice along then. Once the run's turns and record are on screen, a choice goes onto them, and no step of the run takes one back. Leaving the conversation while its message is put together or its overview is open — another one opened, a new one begun, this one or the whole history deleted, a vault attached — is a no to that message, as **Cancel** is: no overview asks for it, nothing is sent, and its words come back to the field. A conversation opened comes on screen only where nothing else happened on screen since the click; when it does, a message begun since the click goes nowhere either. A message whose vault went meanwhile goes nowhere, wherever it was started; a run asked again of another model, started apart from the field, keeps its overview when the user opens another conversation or begins a new one. A skill started from the workshop, and a run asked again of another model, start nothing where the user left the screen or deleted the whole history while they were being put together, and a regression run of skills brings back the conversation that was open — as it is now — only where the user did nothing on screen meanwhile; its own conversations it deletes without a step on screen, and it takes no message before the screen is back. A conversation opened does not come on screen where a run began since the click. An action at a selection waits its turn like a message: one run at a time, also while a run asked again is being put together; and a server's prompt goes only from where its **Send** was pressed.
3. **A conversation's writes go one after the other,** in the order they were made: a later one is never overtaken by an earlier one. A conversation is read only after them, and read again where a write, a deletion or a **Delete all** was asked for while it was read.
4. **A conversation the user deleted, or a history cleared,** while a run was on its way stays deleted — also where the deletion comes while the run's end is being written. The run's ledger entry stays: the month's usage counts what was asked. Whether a conversation is deleted counts once its deletion is done: no write that comes afterwards writes it back, and a deletion that fails takes nothing back — what is chosen before, during or after it is kept. The deletions of one conversation are counted: one that fails takes back only itself, never another of the same conversation or a **Delete all**. A run's end decides whether its conversation is gone once no deletion of it is on its way any more, by what they came to. A conversation whose deletion was asked for takes no more messages; nothing is asked again of it — a run asked again goes nowhere once its original is being deleted —, and nothing is learnt from it: a review of it is cut off, and neither the review nor a run of the conversation lays down a draft whose turn in the list of drafts comes after its conversation or the whole history went. **Delete all** deletes the conversations of the vault on screen — known by the vault's data key, also through a host the shell made anew — and takes off the screen only what it deleted; it clears them once the writes on their way have landed, and what is written or read of a conversation meanwhile waits for it. It stops whatever of its vault is on its way — a message, a run asked again, a door, a routine, a regression run, also one still being put together —, counted from the moment each action began, and what it clears on screen it clears only while its vault is the one on screen, a notice about anything else staying. A conversation leaves the history and the screen once its deletion is done, wherever they show it, and a notice about it goes with it. A vault attached lists its conversations once a **Delete all** on its way is through, and again where one came meanwhile; one whose deletion is on its way stays listed until that deletion is done. Expiry deletes like any deletion, and nothing that was in use when the list was read, nothing on screen and nothing written since. The app's own deletions — a regression run's scenarios, a routine's previous run — go to their own vault; one that fails keeps the conversation and stops nothing: the routine keeps its note, the regression run its scenarios. A store counts what is not there as removed.
5. **What a run sent stays its own:** its record keeps the redaction it went with (`RunMeta.redact`), whatever is chosen afterwards.

## Addendum 2026-10-27: a new host of the vault while a run is on its way

The shells hand the session a new host whenever what it is built of changes — on the desktop the vault's adapter or its query service (the index rebuilt, the password changed, a sync service connected), on the phone the vault object —, the same vault included. The session treated every new host as a vault switch: what was on its way stopped, the screen began anew, and the history was listed again. A run it stopped still wrote its conversation, but the new host's history did not show it; and a run that answered just before the new host came laid its answer into the vault through the old one.

1. **A new host stays a vault switch.** Keeping a run, an agent's session and the server connections across a new host of the same vault was weighed and dropped: a rebuilt host can carry a change that matters for what may go where — an encrypted workspace, new folder rules —, and what is on its way would go on under the old host's rules, which nothing tells apart from a rebuilt index. What is on its way stops, as before.
2. **What the stop costs is no data.** What a stopped run wrote enters the history once the new host's listing is through, as the vault then stores it (`listStopped`): a conversation deleted meanwhile, cleared by **Delete all**, never written or not this vault's reads as nothing, and one more attaching since the reading lists its own vault anew. A conversation the user opens again while the stopped run is still on its way shows the run's end once it comes, as decision 1 of the addendum of 2026-10-26 has it (the run's end is on screen while it is written), and the next message keeps its turns; a reading that comes while that end is written reads it (decision 3 there), and an opening reads again where the end was written while its reading came back — between the reading's check and the screen the old state would otherwise come on screen after the run had ended, off screen for the run's end, and the next message would write over its turns.
3. **Nothing is laid into the vault through the host that was.** A run that answered before the new host came goes on through neither host: an action at a selection lays no round, a reply in a comment thread is not posted, a transcript lays no round, an answer kept as a note is not written, a routine keeps no note and a folder's log writes no entry — each answer stays in its conversation, which the history lists, and a recording stays to be written down again. Each stop stands right before its write, behind every step that waits; a write already under way when the new host comes finishes as it began. A routine's previous conversation goes as it would: it is app data of the same vault, not one of its notes.
